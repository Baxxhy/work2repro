## 研究中心

需求驱动测试的核心目标，是在软件违反用户需求时给出失败信号。当前证据提示，应同时调查测试结果是否依赖真实被测行为，以及输入和判定条件是否能区分违反需求的行为。

建议将三个技术痛点组织为测试替身边界、输入区分度、观察与断言的信息保留。后两项属于判别能力的两个相互关联方面。无需把它们包装成三个互不相关的问题。

此前8/44、7项目的业务缺口统计沿用原义，不能用作这三个新类别的发生率。本轮是4个新增关注案例的定向复核，尚未完成325条的重新标注。

## 痛点一，测试替身可能越过被测行为边界

### 真实证据

Req2Test任务 `coddy-agent/features/ask_mode_http.feature:22`，生成代码位于 `results/test-generation-20261114/req2test/tasks/af2db3aaa3d3aed0e730/generated/external/httpserver/bdd_ask_mode_e2e_test.go`。

需求要求agent模式的流式请求写入文件、模型获得完整工具集、transcript报告agent模式。生成代码存在

```go
w.transcript = mode
// 后面检查
if w.transcript != mode { /* error */ }

w.toolNames = []string{"full-agent-tool-set"}
if len(w.toolNames) == 0 { /* error */ }
```

会话模式的观测值来自请求参数赋值；工具集来自测试自己构造的常量。注入runner又直接调用os.WriteFile。HTTP请求仍真实执行，文件存在检查也确实检查文件系统，但它没有验证模型工具执行产生文件这一链路。

原评分通过，138/388个变异被杀死。测试对某些行为有检出能力，三个局部检查的业务依赖仍存在缺口。250个存活变异没有全部归因。

轨迹节选显示Agent读取保留的HTTP测试及生产API，并表示只实现所选agent模式场景；末尾明确没有运行测试。本轮不据此推断它有意降低检查标准。

CoreShop此前用本地数组模拟订单，是同类补充。两个独立项目均出现测试自身构造结果的情况，但仍没有这类问题的全量比例。

### 技术困难与拟解决问题

测试需要替代外部模型或基础设施，又必须保留需求指定的生产行为。现有注入点可用于某项隔离测试，并不自动适用于当前业务场景。拟研究怎样判断断言值来自真实被测行为、替身返回值还是测试常量，确认替身没有替代本应验证的功能。

生活解释为验证“系统是否把订单送到商家”时，测试自己往商家订单列表放入一条记录，再检查列表里有没有它。这个解释是类比，coddy与CoreShop为真实实验案例。

## 痛点二，合法输入可能无法区分合理的错误实现

### 真实证据

TSB任务 `gromacs__gromacs.665ea4c`，`generated/test_text_workflows.py` 的 `test_editconf_explicit_path_and_transform`。

```python
# 初始三个坐标均为1.000
p = run('editconf', '-f', source, '-o', target,
        '-translate', '0.5', '0.5', '0.5', cwd=tmp_path)
assert lines[2][20:44].split() == ['1.500', '1.500', '1.500']
```

原始坐标与平移量各轴相同。即使实现把dx和dy对应关系交换，数值结果仍相同。局部计算确认正确与交换实现都得到(1.5,1.5,1.5)。不同平移量下，例如(0.1,0.3,0.7)，才得到不同结果。

这里证明特定输入无法区分特定错误，没有证明官方变异池包含轴交换变异，也没有重新运行GROMACS。完整测试还检查stdout和文件等属性，若错误实现额外破坏这些属性仍可能被检出。当前反例仅要求轴映射错误且其他输出格式保持正常。

### 技术困难与拟解决问题

生成输入既要合法、期望值可算，又应让需求规定的对应关系在错误实现中产生可观察差异。对称、默认或退化输入可能使正确与错误行为等价，精确断言也无法补救。拟研究怎样依据需求选择有区分度的输入，避免不同角色、对象或参数被意外置成相同值。

本项当前只有一个直接局部计算案例，跨项目重复性尚需验证。此前zoxide缺少重复参数属于输入遗漏，与对称输入无区分度有区别，不并入同一根因计数。

## 痛点三，断言提取的结果特征不足以保留需求差异

### 真实证据

TSB任务 `burntsushi__ripgrep.3b7fd44` 的 `generated/test_suite.py`。

```python
objs = [json.loads(x) for x in p.stdout.splitlines()]
assert [x['type'] for x in objs] == ['begin','match','end','summary']
```

规格JSON Lines条款明确要求data字段、匹配行、行号、绝对字节位置和子匹配。该测试只提取事件类型序列。

本轮直接提取原测试函数AST，将run替换为返回四个仅含type、完全没有data字段的JSON对象，其他条件设置为退出码0、stderr为空。原测试函数通过。这是局部判定核验，未调用被测程序，也未执行官方评测。其余测试含普通文本匹配检查，但未发现补足此JSON结构检查的其他--json调用。

原任务套件Validity 91.67%，10/117个变异被杀死。这个总分不能单独归因于JSON断言。

Req2Test e-petitions此前全页分别检查标题和人数、没有绑定同一条目的案例，是另一项目中的明确观察范围缺口。rnr只检查帮助前缀亦为补充。

### 技术困难与拟解决问题

即使输入有区分度，测试仍需保留软件输出中体现业务错误的信息。存在性、类型、数量和文本前缀等粗粒度特征，可能将许多不同输出映射为同一个检查值。拟研究怎样保留需求相关字段、对象关系和作用范围，使违反需求的输出触发断言失败。

生活解释为查看购物小票时，只确认有“商品”和“金额”两栏，却没有检查买了什么、多少钱。该小票仅为类比。

TSB任务 `doxygen__doxygen.966d98e` 的 `test_compare_stdin_changed_setting_and_env_modes` 设定HOME为/tmp/home，对同一配置分别调用-x和-x_noenv。断言前者含/tmp/home/out，后者含$(HOME)/out。

## 浅层测试扩张先作为研究线索

GROMACS原评分n_test_functions为191，Validity 90.05%，5/148即3.38%的变异分数。该字段在本任务体现参数化展开的测试项，不能写成191个源码测试函数；n_tests为28,459，是跨原实现及变异的执行计数。

轨迹节选中Agent称规格对help/parser/text workflows有明确契约，最终也说明覆盖共享CLI与文本流程。要判断是规格结构、领域知识、预算或生成规划导致，需要其他任务及完整轨迹对照。因此本轮不把预算倾向列为已确认根因。
