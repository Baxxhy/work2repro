# 场景已经写清楚，Req2Test为什么仍然失败

日期为2026年11月16日。范围固定为已发布160条子集，按官方排除1条后计分159条。配置为Codex CLI 0.160.0、GPT-6 Luna、medium、TH视图。读取全部160条正式执行记录、原始任务、生成文件索引和已有轨迹节选。本轮新增模型生成和评测次数均为0。

## 先说结论

场景明确降低了“要检查什么”的歧义。实际任务还要求Agent把文字步骤接入真实项目，准备对象、注册步骤、选择服务、遵守语言版本和框架约定。当前失败大量发生在这些环节。

159条计分任务中44条通过、115条失败。115条失败里，69条在文件交付、编译、服务容器、步骤绑定或套件入口上失败。另外46条官方归为assertion_failure，逐条查看日志后，28条直接错误是运行异常，18条是检查结果不符。18条还包括前置对象不存在等检查，不能直接当成18条错误预期值。

最直观的对照是python-docx有18/20条通过，CoreShop有1/20条通过。这个结果支持继续研究“具体场景如何落实到项目操作”，而仅凭场景篇幅推断测试难度会漏掉重要因素。

## 一、全部失败到底卡在哪里

下表按每个任务当前执行记录的直接失败点分类，每条任务只计一次。保留原始官方类别，新增分析类别另列于CSV。

|---|---:|---:|---|

|服务容器初始化失败|17|14.78%|PHP服务容器启动失败，16条明确指向生成Context的依赖绑定，1条日志尾部截断|
|步骤未绑定|13|11.30%|场景文本找不到匹配的执行函数，部分任务还同时存在其他错误|
|测试套件入口配置错误|5|4.35%|5条Coddy均报selected suite requires explicit Options|

## 三、真实例子说明具体哪里出了问题

### 例1，四步算购物车税，前面实际还有30步准备

任务为coreshop/features/domain/cart/cart_units_taxation_gross.feature:55。

原始Scenario全文为

```gherkin
Scenario: Create a new cart for a different Tax Rate, add a product and calculate subtotals
  Given I add the product "CH T-Shirt" with unit "Carton" to my cart
  Given I add the product "CH T-Shirt" with unit "Pieces" to my cart
  Then the cart total should be "36590" including tax
  Then the cart total tax should be "2616"
```

中文就是把一箱和一件T恤加入购物车，检查含税总价36590和税额2616。原始Background还要求建立奥地利商店、两套税率与税规则、三种商品单位、多种商品及其单位换算和价格，共30个准备步骤。

轨迹显示，Agent读取TARGET_CONTRACTS.md，查找CartModifierInterface、对象工厂和fixtures.yaml，最后表示无法确认可靠的对象准备方式，未提交代码。最终官方状态为generation_failure，生成文件数为0。

这条的直接原因是未完成前置业务对象和依赖的组装。Agent的“可见信息不足”是它自己的解释，尚不能当作仓库确实无法提供信息的证明。15条未交付任务中，14条最终消息涉及前置对象或步骤重建困难，另1条Sylius涉及UI通知与API检查契约的对应困难。

### 例2，新增样式的步骤写清楚了，初始文档却选错了

任务为python-docx/features/sty-add-style.feature:7。

原始需求包括

```gherkin
Given a document having known styles
When I call add_style('<name>', <type>, builtin=<builtin>)
Then the document has one additional style
```

Examples明确包含Heading 1、Inline Code、List Bullet和Shipments。生成代码sty_add_style_steps.py第24—26行直接使用默认文档

```python
context.document = Document()
context.styles = context.document.styles
context.initial_style_count = len(context.styles)
```

第33行再调用

```python
context.style = context.styles.add_style(name, style_type, builtin=builtin_value)
```

实际日志为`document already contains style 'Heading 1'`。同一Scenario Outline的4组例子中，2组通过、2组出错，整个任务判失败。默认文档已包含部分待添加样式，准备阶段没有保证“待添加名称尚不存在”。轨迹显示模型读过场景和相关代码，只做了py_compile语法检查，没有得到完整场景运行反馈。

这例的困难很具体，Given只说“已知样式的文档”，模型还要结合后续Examples选出合适的初始状态。

### 例3，页面已经打开，读取列表时选错了选择器语法

任务为e-petitions/features/suzie_views_all_petitions.feature:12。

需求要求建立签名数500、500000、1000的三个请愿，浏览Open列表，检查数量为3，并按签名数顺序显示。生成代码all_petitions_steps.rb第14—17行为

```ruby
Then(/^I should see the following ordered list of petitions:$/) do |table|
  expected = table.raw.flatten.map(&:strip)
  actual = page.all("ul.petition-lists li").map { |item| item.text.strip }
  expect(actual).to eq(expected)
end
```

实际读取列表时报`ERROR: Invalid expression: ul.petition-lists li`，没有走到列表相等断言。另一个任务同文件场景第24行也对`ol li`报同类错误。这两条证明选择器表达式没有被当前项目框架正确接受；框架默认选择器与生成代码的具体对应需要继续核对支持文件。

它们在官方表中都归入assertion_failure，实际直接失败点是观察页面元素的调用。

### 例4，接口路径包含相同参数，字符串顺序却导致失败

任务为algorand-sdk/features/unit/v2indexerclient_paths.feature:163。

原始Examples给出的期望路径为

```text
/v2/assets/100/transactions?currency-greater-than=0&rekey-to=true
```

生成IndexerClientV2PathSteps.java第31—37行读取getRequestUrl()，提取路径和查询串，再直接比较完整字符串。执行日志中的实际值为

```text
/v2/assets/100/transactions?rekey-to=true&currency-greater-than=0
```

两边参数名和值相同，仅排列不同。同项目第41行场景也出现两项参数互换顺序导致失败。这里能确认比较对表现形式敏感。需求写了具体路径，因此仍需结合参考步骤的比较方式确认官方预期是否允许参数重排，暂不直接判定为错误断言。

该测试还将“mock server recording request paths”写成空步骤，通过getRequestUrl读取构造结果。它实际观察的是请求构造阶段，是否与发送后的路径一致需另行核对。

### 例5，Java代码用了当前编译级别不支持的方法

任务为algorand-sdk/features/unit/abijson.feature:33。需求要求构造Method对象、序列化为JSON、与给定文件比较并检查反序列化结果。

AbiJsonSteps.java第41行读取文件时使用

```java
String expected = new String(input.readAllBytes(), StandardCharsets.UTF_8).trim();
```

编译日志明确报告`cannot find symbol: method readAllBytes()`。输入环境说明已经写明运行在JDK 11、按固定Java 8 release编译。生成代码未遵守这个约束，场景还没开始运行就失败。

该条轨迹首次rg搜索遇到Permission denied，随后通过find、grep、sed继续读取了文件。不能仅用首次搜索失败解释这个编译错误。

### 例6，步骤函数已经写了，测试入口漏了框架配置

任务为coddy-agent/features/acp_permission_answers.feature:23。需求是编辑器拒绝授权后，命令仍然需要权限。

生成bdd_acp_permission_answers_test.go第21—34行构造godog.TestSuite，注册ScenarioInitializer后调用suite.Run()，没有设置Options。官方执行日志为

```text
selected suite requires explicit Options
```

该任务没有实际运行场景。相同错误还出现在background_tasks:32、cli_tui:140、cli_tui:93、subagents:8，共5条。

## 四、当前运行条件也会影响这些错误能否被发现

1. **生成阶段可以运行可见工作区，正式评测反馈在提交后提供。** 后续核对锁定官方源码及运行日志，确认runtime packs支持编译和本地运行。160条中找到56份非空运行包日志，包括9条go test、2条behat-scenario。TH视图隐藏目标实现，本地运行能发现部分接入问题，但可见实现与正式完整实现存在差异。
2. **rg被官方主动屏蔽。** 160份轨迹节选中151份出现Permission denied，通过的44条中也有39条遇到。后续核对toolset.py确认rg属于官方MASKED_TOOLS，这符合统一工具集的沙箱设计。上一版把它称为环境问题的判断已纠正。多条轨迹随后使用find/grep/sed继续读取。
3. **一个Scenario Outline会运行多组Examples。** python-docx新增样式例子已经展示同一条任务部分例子通过、部分失败。这会进一步放大“看起来只有一个场景”和实际需要满足条件之间的差别。

## 五、现在能回答的问题

当前低通过率的直接来源，大量是“文字步骤到项目代码”的落实失败，包括前置状态、测试步骤绑定、依赖注入、API类型和框架上下文。18条显式检查失败还要继续区分准备错误、调用错误、观察方式和预期值，当前数量不能直接解释为业务断言不足的发生率。

后续研究优先核对两类可检验因素。一类是给定明确业务条件后，是否能构造真正满足条件的对象及关联状态。另一类是在真实项目中，是否选择了能够观察需求结果的调用与比较方式。语言版本、测试入口等兼容故障单独登记。

之前用TestSuiteBench的测试级Validity和Req2Test的任务级Pass@1判断前者更容易，依据不足。此次更有解释力的证据来自Req2Test内部项目差异和逐步失败日志。
