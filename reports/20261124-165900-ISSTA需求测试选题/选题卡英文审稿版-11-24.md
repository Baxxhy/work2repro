# Which Requirement Distinctions Do Generated Assertions Enforce?

**Method.** Requirement-guided assertion replay

## Motivation
**Problem framing.** In TestSuiteBench, 61 of the 83 tasks with validity of at least 80% had a mutation score of at most 25%, among 165 tasks overall. In the archived Req2Test-Bench run, 316 of 538 passing scenarios left at least one scored mutant alive, across all eight projects. A manual review of 44 passing scenarios in a fixed subset found eight business-behavior gaps across seven projects. Four concerned assertions, three the action and one the observation. The count pertinent to assertion repair is four of 44 (9.1%), each from a different project.

The python-docx requirement fixes document order. With the paragraphs held in place, the existing check accepted all six permutations of three distinguishable tables from the original file. Five violated the requirement, even though the test killed all 93 official mutants. In ast-grep the two matching files may appear in either order. The existing check accepts two copies of one file, while demanding one fixed list would reject a permitted order. TestPrism gives a verdict for a suite on each implementation. Liang et al. measure the effect of an expected result when the input has one normalized answer. For an assertion over multiple possible observations, the question is which distinction the clause requires and whether the original code actually enforces it.

**Why now.** The archived public requirements, sample inputs and generated test files make it possible to locate a test’s readout and replay its original decision. In 2026, Ma and Eisty compared requirement-generated oracles with manually specified judgments on ten Java bugs, Liang et al. compared expected-output predictors on fixed inputs, and TestPrism evaluated suites on both lawful and faulty implementations. Those comparisons give a direct question for the new data. Once the public clause is available to an editor, does the original assertion’s verdict on a particular constructed result add anything to the repair? [Ma and Eisty](https://arxiv.org/abs/2607.10277) $\cdot $ [Liang et al.](https://arxiv.org/abs/2609.05879) $\cdot $ [TestPrism](https://arxiv.org/abs/2610.12289)

**Why prior work stopped.**
- `arxiv:2610.12289` (arXiv 预印本 v2 2026): TestPrism evaluates generated suites on hidden panels of valid and faulty implementations, and TestHelix uses peer implementations to cross-check and revise tests.
  - _Did not do_: A verdict at that level leaves open which assertion and fixture-dependent relation accounted for the pass or failure.
  - _Structural reason_: That attribution needs the public clause’s judgment and the original assertion’s verdict on the very same observation.
- `issta:du2026` (ISSTA 2026 主会 2026): Du et al. use surviving mutants to augment assertions on existing inputs and evaluate the added checks on real Defects4J bugs.
  - _Did not do_: Their study leaves open whether an edit chosen before the author can execute an implementation transfers to independent faults.
  - _Structural reason_: Their editor selects assertion changes using evidence from runnable program mutants.
- `arxiv:2609.05879` (arXiv 预印本 2026): Liang et al. separate the faults a fixed input could expose from those detected by its generated expected answer.
  - _Did not do_: The study excludes tasks with multiple accepted outputs or a special judge, leaving tests that check only selected output relations outside its scope.
  - _Structural reason_: Its verdict depends on reference consensus over one normalized answer per input.
- `tosem:agoraplus2025` (TOSEM 期刊 2025): AGORA+ learns invariants from observed application programming interface traffic, turns them into executable assertions and checks seeded errors and live services.
  - _Did not do_: It leaves open how a previously written assertion judges a requirement-specific alternative before any traffic is available.
  - _Structural reason_: Its source of evidence about admissibility is a collection of actual requests and responses.
- `acl:2026.findings-acl.683` (ACL Findings 2026): PROBE uses source-level relations across functions to derive properties, constructs incorrect implementations that satisfy them and refines the properties.
  - _Did not do_: It leaves open which actual value an existing requirement-derived assertion misjudges when the implementation is hidden.
  - _Structural reason_: Its refinement signal comes from source-derived constraints and counter-implementations.

**What changes when the gap closes.** A test author could show the maintainer the clause, a value the public fixture justifies and the exact decision the existing test makes on that value. In a TestPrism-style evaluation, that record could explain a particular suite judgment. In Du et al.’s independent-fault setting, it would let an evaluator ask whether a source-justified edit selected before execution catches a bug and still accepts the permitted alternatives.

## Method
**Pipeline.** Choose a public clause that a frozen test’s action reaches and identify where that test receives the result. Derive a typed result from the fixture, vary one required relation at a time where the evidence permits, and run the original test-side readout on each supplied value. Compare the clause judgment with the old assertion’s verdict and use the assigned differences to select one predicate edit. Freeze the diagnosis and proposed edit before an independent evaluator checks mapped bug/fix pairs and implementations that realize allowed variations.

### Background

1. **Identify what the test can observe** (`S1`)
   - Screen each public requirement and frozen test by project. Record the clause, fixture, action, static receiving site and the counts for eligible, ambiguous, untriggered or unobservable units. Treat the 14 of 165 TestSuiteBench specifications with explicit order freedom as leads. Reserve fresh TestSuiteBench repositories before tuning. The three replays and 44 reviewed Req2Test-Bench passes are development evidence, and those 44 passes already span all eight Req2Test projects. Use one row per project, test, quoted clause and fixture. Record the task identifier, fixture revision, action line, result-receiving line and intended assertion. Trace the value from the call, stream or file through the test’s own reader. Give every screened unit a status and count distinct tasks separately from distinct units.
   - _Why:_ A predicate edit can address a decision about an observed value. Screening records how many tasks instead need a different action or an accessible result and identifies which projects can supply independent evidence.

### Read the rule and replay the check
*Find a specific value on which the public clause and the existing test disagree.*

2. **Bind one clause to the public fixture** (`S2`)
   - Freeze the extractor version, prompt and settings. For each command or scenario, obtain the exact clause span, other affected conditions, fixture keys and source for the return contract. Verify that each key can identify an item in the fixture and the received result. Represent membership by key counts, exact order by a key list, and precedence by ordered pairs. Construct a lawful value of the required type. For partial orders, repeatedly choose the earliest fixture item whose required predecessors have been placed. Record unsupported conditions, types, keys and cycles as unknown. In the Word generation trace the middle table had distinctive cell text. Later inspection also distinguished the first and last tables by their structure.
   - _Why:_ The same item can be optional, mandatory once or required repeatedly depending on the command. A label is meaningful only when the clause, test setup and item identities support it.
3. **Compare the clause and the original assertion on each result** (`S3`)
   - Starting from the lawful seed and fixture keys, allow one extra same-type key only if its absence is documented. Keep non-edited fields fixed. Enumerate at most two insertions, deletions, substitutions or swaps, sorting by edit count, alphabetical operator sequence, positions and serialized keys. Keep the first 64 distinct typed raw values, including the seed. Retain each value’s first edit path, order and multiplicity. Base neutral identifiers and presentation order on a digest of the unit and raw value before labeling. Mark a value lawful when the applicable conditions hold, or a violation when only the focal clause fails. At the receiving site run the existing parsing and assertion on that same value. Keep source, edits, both judgments, their signed difference and the failing line privately. An unresolved clause, unfaithful return or unrelated failure makes its own judgment unknown. The original Word assertion accepted the correct order and all five wrong orders on genuine objects read by python-docx 1.2.0.

*A is the old assertion’s verdict on the supplied result and L is the clause’s judgment. A value of 1 means acceptance. D is +1 for a missed violation, $- 1$ for a rejected lawful result and 0 for agreement. Leave D unknown if either judgment is unknown.*
$$ D=A-L,\qquad A,L\in\{0,1\} \tag{1} $$

   - _Why:_ The two judgments refer to the very same supplied value. A mismatch demonstrates a decision error on that value, while product reachability has its own endpoint.

### Choose a predicate edit
*Test whether attaching the right feedback to the right result matters.*

4. **Use the assigned disagreements to select one edit** (`S4`)
   - Give both editors the same public materials, frozen rows and old verdicts. Group by old verdict, result shape (type, fields, length) and the first generation path’s operator sequence. Within each group, sort agreeing and disagreeing rows by the serialized observation key and zip the two lists. In one arm keep each matched row’s difference, in the other exchange the two differences within each pair. Subtract the assigned difference from the old verdict to obtain the required answer. Editors and filters receive only their own assignment. Hide true labels, pair identities, seed flags, reasons, sign-selected examples and the private audit. Keep unmatched and unknown rows visible without targets. Each editor proposes up to four edits to one predicate in one response. Keep edits reaching the intended check and matching every assigned target. Minimize inserted, deleted or replaced syntax-tree nodes, then break ties by source position and code text. No targets or no qualifying edit retains the original. After commitment release the first example of each observed nonzero sign with its seed and report matching counts.

*For a matched row, the assigned disagreement D* and the old verdict A give the verdict Y that the edited assertion must return. Pairing rows with the same A keeps Y binary.*
$$ Y=A-D^{\ast} \tag{2} $$

   - _Why:_ Permuting the association preserves each pair’s observations, old verdicts and feedback values. Giving the same assignment to the editor and filter makes any downstream difference attributable to where the feedback went, subject to the measured controls.

### Verify the diagnosis and its effect on products
*Establish what the public evidence supports and evaluate a committed edit on independent implementations.*

5. **Measure what development traces add to diagnosis** (`S5`)
   - Freeze the target-free diagnosis. Give a separate copy of each unit to the same extractor with the same time and witness allowance and any available development implementation traces. Two readers independently judge the source-based labels without the arm identity or old replay verdict. Reproduce the original verdict and report confirmed, disputed, unknown and unavailable outcomes against both the screened and eligible denominators in each arm. Log the source revision, fixture and raw return for each development trace. 【author decision: specify which development implementations and runs supply traces before comparing the two conditions.】 Hide the proposed clause label as well as the old verdict from both readers. A confirmed discrepancy requires both readers to support the recorded label and a fresh replay to reproduce the old verdict. Report units with at least one confirmed discrepancy, including units confirmed only with traces, and retain fully agreeing units in the denominators.
   - _Why:_ The comparison measures the extra diagnoses available from traces and the share that independent readers can verify when only public sources are available.
6. **Give direct clause translation the same opportunity to edit** (`S6`)
   - Compare the original, a blind edit under the same limits, direct clause translation, unguided same-type changes, and the aligned and shuffled feedback edits. The direct editor gets the full public clause, fixture, frozen action, readout, original assertion and the same unlabeled observations. It can compile and run its own predicate under the same call and replay caps and commit one predicate edit. The evaluator keeps its labels, signed differences and assigned targets private. Log calls, replays, reader time and abstentions for each condition. Carry every abstention into evaluation as the original test. The blind editor reviews the original predicate with the public materials. The direct editor writes the stated count, order or predecessor check from those materials. The unguided operator chooses type-compatible items and positions without consulting the clause. Record exactly what each editor received and the committed change. Keep fixture, action and readout fixed in every condition.
   - _Why:_ Direct translation already has the information needed to express a documented rule. Its outcome tests whether replaying the old decision brings a benefit beyond writing that rule down.
7. **Score independent faults and permitted alternatives** (`S7`)
   - Blind reviewers lock each project, bug identifier, buggy revision, own fix, fixture, command and clause citation, plus independently observed implementations exhibiting documented lawful variation. 【author decision: predeclare the independent archives and which releases or separate implementations qualify as distinct lawful alternatives.】 Execute the complete test under the same setup on both revisions. Credit the bug once per project if a mapped test fails at the intended check on the buggy revision and passes on its own fix. Count newly gained and lost bugs against the original, divide their difference by all eligible bugs in each project and average the project rates. Separately count previously accepted lawful alternatives newly failing at the intended check over all eligible lawful alternatives. Report unrelated failures, unavailable environments and independently attributed benchmark mutants separately. An empty panel leaves its endpoint unassessed. Only three of 833 archived survivor pairs currently carry explicit clause attribution.

*In project p, $G_{p}$ and $M_{p}$ count gained and lost detections among $B_{p}$ eligible bugs. $J_{p}$ counts previously accepted lawful alternatives newly rejected among all $V_{p}$ eligible alternatives. A zero denominator leaves that endpoint unassessed.*
$$ g_p=\frac{G_p-M_p}{B_p},\qquad r_p=\frac{J_p}{V_p} \tag{3} $$

   - _Why:_ Producing a local counterexample demonstrates how the assertion behaves. A matched bug and fix show whether a real product fault is detected, and independently realized lawful behavior checks the cost of tightening the assertion.
