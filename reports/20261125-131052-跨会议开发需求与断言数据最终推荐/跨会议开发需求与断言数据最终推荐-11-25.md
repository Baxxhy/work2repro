# 跨会议开发需求与断言数据最终推荐

北京时间 2026-11-25 13:10:52 开始。本轮合并用户提供的跨会议清单和此前的逐项核验，筛选有正式录用记录、跨应用领域、能够用非浏览器方式检验功能需求的数据。研究对象是从开发需求生成可执行测试，以及已有断言对错误结果的漏检与对合法结果的误拒。

## 为何把 RepoGenesis 放进主实验

逐项核对正式评测的 **30/30 个项目**，均有独立的需求 README 和项目参考测试。读取 30 份需求文件，并扫描测试目录的 **95 份 Python 或 Java 源文件**（含测试辅助代码），常见浏览器驱动标识命中 0 份。论文使用 HTTP 接口等黑盒方式评测，项目涉及项目管理、聊天、文件管理、游戏与排课等多种业务。此核验覆盖公开需求与测试文件，尚未启动 30 个服务。[公开评测项目注册表](https://github.com/pzy2000/RepoGenesis/blob/54a1dd49a51eb12666f7c394f1879c02df5b91b8/eval_harness/constants.py) · [逐项目文件核对](正式评测项目清单-11-25.csv)

井字棋用例能直接说明昨天关心的两种错误。

- **漏检。** 测试按 X、O 交替落子，X 的三步占据第一行三格。原测试最后接受“已结束”或“平局”，只在“已结束”分支检查胜者。我们读取原测试的末尾断言，对三种结果求值。X 获胜通过，错误的平局也通过，O 获胜被拒绝。这里核实的是原断言的判定，未观察到服务实际把该局判平。[验收测试的落子与断言](https://github.com/pzy2000/RepoGenesis/blob/54a1dd49a51eb12666f7c394f1879c02df5b91b8/repo/Tic-Tac-Toe/tests/test_game_api.py#L52) · [三种结果的逐项记录](项目计数与断言核验-11-25.json)
- **误拒。** 同一服务的排行榜需求规定按胜场降序、平局不计胜场，未指定同分玩家之间的排序。可以设两名玩家胜场相同，用两种顺序检查同一断言。只认其中一种次序会增加需求未规定的限制。这个例子给出由规格推导的对照，不代表在此用例中已经测到模型误拒。[排行榜需求](https://github.com/pzy2000/RepoGenesis/blob/54a1dd49a51eb12666f7c394f1879c02df5b91b8/repo_readme_verified_python_no_t/Tic-Tac-Toe/README.md#L150)

**项目统计采用 30 个唯一评测项目作为分母。** 论文的 1,258 个 API 和 2,335 个测试是全量统计；表三评测集的底行写 294 个 API 和 805 项测试，30 个项目行分别加总为 331 和 810。逐行数字与求和结果已归档，以上两组数字不用于评测分母。[ACL 定稿表三](https://aclanthology.org/2026.acl-long.415.pdf#page=3) · [逐行复算](正式评测项目清单-11-25.csv)

## 附件中其他候选的取舍

- **SWE Atlas Test Writing** 最适合与仓库级写测试方法做对照。公开版本有 90 个测试任务。例如 keyBy 的题面已经给出函数及五个要覆盖的场景，评分还包括工程质量。研究“从开发规格自行识别应检查的规则”时，直接拿这种题面对照会额外提供验证目标。**IntentionTest 和 Sakura** 也适合研究如何把验证意图或测试场景写成代码。Sakura 的文字由已有测试反推。[SWE Atlas 作者说明](https://labs.scale.com/papers/sweatlas) · [SWE Atlas 题面](https://github.com/scaleapi/SWE-Atlas/blob/b3cdddf44414c0ccca50c6e89fe978bb4d844d26/data/tw/tw-6902ef3ab97fe23e2ad271ee/instruction.md) · [IntentionTest](https://github.com/code-philia/IntentionTest) · [Sakura 会议论文](https://conf.researchr.org/details/issta-2026/issta-2026-research-papers/21/Sakura-An-Approach-for-Generating-Complex-Tests-from-Natural-Language-Test-Descripti)
- **Doc2Feat-Bench Verified（ASE 2026）**有真实开发者随功能 PR 更新的文档。若论文后续要强调真实开源功能变更，可从既有清单的 5 个项目、55 项非浏览器新增功能外部验证。眼下 RepoGenesis 已提供业务接口的验收规则，PBT-Bench 已提供真实库与错误版本，三套组合已有明确分工。[正式论文](https://doi.org/10.1145/3832783.3837489) · [已核对的功能清单](../20261125-003801-非浏览器开发需求测试数据/逐项筛选与来源-11-25.csv)
- **TC-Bench（ICLR 2026）**适合研究编程题的错误程序判别，**E2EDev（ACL 2026）**覆盖网页项目的需求与端到端交互。前者的应用场景与函数专项重叠，后者的原生执行方式超出此次范围。[TC-Bench 正式论文](https://proceedings.iclr.cc/paper_files/paper/2026/hash/4050d012bcba07685bd177ef3a381054-Abstract-Conference.html) · [E2EDev 正式论文](https://aclanthology.org/2026.acl-long.1618/)

## 复核与证据范围

本轮读取论文定稿、作者固定版本的文件和上一轮的逐项核验，重新检查了 RepoGenesis 的项目和井字棋样例。案例仅说明该断言接受了一个具体违规结果；30 个项目中的漏检、误拒发生率仍需逐条标注。三套数据分别以服务项目、库任务、函数规格为单位，分别报告数据与效果。[上轮 PBT-Bench 与 Expecto 样本清单](../20261125-092345-已录用开发需求到断言数据/已核对的公开样本标识-11-25.csv)
