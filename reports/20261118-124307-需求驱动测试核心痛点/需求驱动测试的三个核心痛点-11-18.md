# 需求驱动测试的三个核心痛点

**研究问题：当开发者把用户需求交给 Coding Agent 写代码时，怎样生成能发现软件违背需求的验收测试？**

两份分析的交集是“测试能通过，仍可能放过需求违例”。复现中，TestSuiteBench 全部 165 个任务的 Validity 为 74.67%，Mutation Score 为 16.11%。Req2Test-Bench 全量队列包含 2,051 条任务，原统计的项目宏平均 Pass@1 为 29.73%，KillComplete@1 为 13.33%。两组指标分别在各自评测协议下解释。后续 308 条隔离复核给出的中断修正估计是 Pass@1 约 30.15%，正式基线沿用原值。[TestSuiteBench 与 Req2Test 统计](../20261117-162415-全任务失败分类与比例统计/全任务失败分类与比例报告-11-17.md) · [Req2Test 全量复核](../20261118-123501-Req2Test308条复核结果/308条复核结论-11-18.md)

## 1. 用例看起来相关，却没有让需求中的关键条件发生

**难点是选对能暴露错误的输入。** TestSuiteBench 的 ast-grep 规格用 Markdown 写明，搜索命令接受多个文件或目录路径。我们的生成测试创建了 `a.js` 和 `b.js`，却只把它们所在的一个目录传给程序。即使程序忽略第二个路径，这条用例也触发不了这个错误。原论文在同一项目中对照两套测试，显式传入两个路径的测试检出了忽略第二个路径的变异，单路径测试漏检。这是论文的独立对照，本案例的结论针对仓库中所引函数。[原始规格](../../data/test-generation-20261114/testsuitebench-specifications/ast-grep__ast-grep.dde0fe0/spec.md#L82) · [生成代码](../../results/test-generation-20261114/testsuitebench/tasks/ast-grep__ast-grep.dde0fe0/generated/test_cli.py#L172) · [TestSuiteBench §3.2](https://arxiv.org/html/2610.13065)

CiRA 从自然语言条件句推导测试描述，DSpec2Test 从 Dafny 形式契约推导测试输入。我们的案例把难点落在真实软件规格到可执行输入的对应上：“有两个文件”和“命令收到两个路径”要求不同的输入构造。[CiRA](https://doi.org/10.1016/j.jss.2022.111549) · [DSpec2Test](https://arxiv.org/abs/2609.29713)

## 2. 测试步骤写了，但没有真正走完产品的业务流程

**难点是让需求中的准备、操作和结果来自同一条真实业务链。** Req2Test-Bench 的 CoreShop 任务用 Gherkin 描述了加商品、用优惠券、从购物车创建订单。生成测试把商品放入本地数组，让匿名订单对象返回这个数组，然后检查商品数。轨迹显示 Agent 尝试查找准备步骤后，主动采用内存实现，并说明没有调用生产服务。测试通过，计分变异检出为 0/200。生成代码、轨迹和调用记录支持“真实转单没有执行”，0/200 描述的是整个任务的评测结果。另一种情况出现在 python-docx，读取页眉代理对象后直接新增节，实际未建立需求所说的已有页眉定义。[CoreShop 与 python-docx 需求、代码和轨迹](../20261117-153624-基于结果与轨迹的痛点分析/基于结果与轨迹的三个痛点-11-17.md)

IntentionTest 已经研究用相似测试指导项目内生成。Req2Test 原论文也发现，其判读的 200 条通过但检出不完整的测试里，120 条缺失信息可在 Agent 工作区找到。真正值得追问的是 Agent 是否用找来的辅助代码建立了所需状态，以及断言观察的结果是否由目标操作产生。当前材料能区分主动绕过和误判准备状态，尚无全量轨迹归因。[IntentionTest](https://github.com/code-philia/IntentionTest) · [Req2Test-Bench §5.4](https://arxiv.org/html/2610.36584)

## 3. 执行了正确的操作，但结果检查丢掉了关键关系

**难点是让断言准确对应需求写明的对象、结果和允许的变化。** Req2Test-Bench 的 e-petitions 要求显示每条请愿及其对应的签名数。生成测试分别在整页找标题和人数。两条请愿的人数即使互换，这些检查仍能满足。交换是从现有断言逻辑推出的反例。TestSuiteBench 的 ast-grep 同一条测试则只检查输出两行，重复两次 `a.js` 也能满足该断言；如果断言把两个文件的输出顺序写死，又会误拒规格允许的换序结果。[e-petitions 案例复核](../20261117-153624-基于结果与轨迹的痛点分析/基于结果与轨迹的三个痛点-11-17.md) · [ast-grep 生成代码](../../results/test-generation-20261114/testsuitebench/tasks/ast-grep__ast-grep.dde0fe0/generated/test_cli.py#L172)

TOGLL 已研究给定单元测试前缀时如何产出正确、有检错能力的判据。SeGa 已在从产品需求生成业务单测时观察到模型臆测断言造成的误报。这里更具体的问题是，把自然语言规格里的对应关系转换成可执行断言，同时保留规格允许的变化。[TOGLL](https://arxiv.org/html/2405.03786) · [SeGa](https://doi.org/10.1145/3832192)

## 取舍与证据范围

**首选围绕痛点 1 和 3。** 两者可以用同一个真实案例讲清楚。输入要让错误有机会暴露，结果检查要能读出这个错误。TestSuiteBench 可作为主要证据，Req2Test 可核对跨项目场景的结果判定。若主攻真实仓库里的业务验收，再把痛点 2 纳入主线，由 Req2Test 提供主要证据。把分数差距放在动机和结果解释里，测试通过率和变异分数各有测量用途。
