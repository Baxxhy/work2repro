## 二、这个研究到底要做什么

### 2.1 为什么需要根据需求生成测试

开发者提出功能需求，AI可以帮助编写实现。接下来仍然需要检查，软件实际表现是否符合要求。

以本次真实数据中的请愿网站为例，需求要求页面展示相似请愿，并显示每条请愿对应的签名人数。如果页面把两条请愿的签名人数显示反了，页面仍能打开，搜索也能返回结果，但用户看到的信息已经错误。

我们希望AI根据需求自动编写测试，执行相关操作，再检查实际结果，从而发现这样的错误。

### 2.2 测试代码具体做什么

一段测试通常包含三部分。

- 准备数据，例如创建两条请愿，分别设置签名人数。
- 执行操作，例如在网页输入关键词并点击搜索。
- 检查结果，例如确认每个标题旁边显示了正确的签名人数。

第三步在代码中称为“断言”。可以把它理解为一条自动判定规则，例如“这条请愿旁边的数字必须是1,023”。条件满足就通过，否则测试报错。

本次实验让Codex读任务、查找允许访问的上下文并生成测试文件，再由官方评测程序运行这些文件。最终得到测试代码、执行记录和检错指标。

## 三、两个Benchmark的输入和输出分别是什么

Benchmark可以理解为一套统一的测试题和评分规则。这里的题目要求AI编写测试代码。

|对比项|TestSuiteBench|Req2Test-Bench|
|---|---|---|
|一条任务有多大|一个软件的完整功能要求|一个项目中的具体需求场景|
|主要输入|软件规格说明，以及测试文件和运行方式的约定|Given/When/Then场景、允许访问的仓库上下文、接口契约和测试框架说明|
|本次生成时看到的实现|以规格为输入，按黑盒方式编写测试|TH视图，目标实现主体及相关行为实现被隐藏，保留规定允许的上下文|
|需要输出|整套可运行测试，包括run.sh和测试文件|把场景中的文字步骤实现成代码，放入规定测试目录|
|测试怎样运行|调用统一路径的executable程序|通过项目原有测试框架执行生成的步骤代码|
|本次规模|锁定版本全部165条有效任务|8个项目各抽20条，共160条，159条计分|

### 3.1 什么叫“规格说明”

**规格说明就是把“这个软件应该怎样工作”写清楚的一份功能要求。**

它可以说明软件有哪些命令、每个命令接受什么输入、应该输出什么、哪些情况要报错、操作之后数据应怎样变化。

TestSuiteBench中的真实任务 `ajeetdsouza__zoxide.67ca1bc` 就提供了这样一份文件。zoxide是帮助用户查找和跳转目录的命令行工具。规格规定它应支持添加目录、查询目录、删除目录、导入数据等功能，还规定数据保存方式与错误输出。

其中一段原文为

```text
executable add [-s|--score SCORE] PATH...
executable query [-a|--all] [-i|--interactive] [-l|--list] [-s|--score]
                 [--exclude PATH] [--base-dir PATH] [KEYWORD...]
executable remove [PATH...]
```

把这些写法翻译成日常语言，就是“可以把目录加入记录，可以根据关键词查目录，还可以删除记录”。方括号里的内容表示可选参数，例如查询时可以要求同时显示分数。

这份规格还明确要求，成功返回状态码0，运行或数据错误返回1，参数写错返回2。状态码就是程序退出时交给调用者的数字，用来告诉调用者操作结果。

因此，这一题要求AI根据整份规格，生成覆盖这些功能和错误情况的一套测试。

### 3.2 TestSuiteBench真实生成了什么

下面是本次Codex实际生成的一个测试函数，保留原始代码。

```python
def test_add_normalizes_accumulates_and_query_formats_scores(ctx):
    _, cwd, _, call = ctx
    p = cwd / "space ü & dir"
    p.mkdir()
    assert call("add", str(p / "." )).returncode == 0
    assert call("add", "--score=2", str(p)).returncode == 0
    q = call("query", "--score", "--list")
    assert q.returncode == 0
    assert q.stdout.decode().splitlines() == ["  12.0 " + str(p)]
```

逐步解释它做了什么。

1. 创建一个目录，名字中包含空格和特殊字符，用来检查这类路径能否正常处理。
2. 调用程序的 `add` 命令，把目录加入数据库。
3. 再执行一次 `add --score=2`，修改该目录的分数。
4. 调用 `query --score --list`，要求程序返回目录及分数。
5. 检查查询成功，并且结果恰好是预期分数12.0及对应目录路径。

这里的 `call` 会启动真实的待测程序。分数12.0对应该规格的计分及查询规则。该函数在官方正确实现上的执行状态为 `passed`。

同一任务还生成了其他测试，共19个测试实例，其中18个在正确实现上通过。整套测试检出了39个计分变异中的8个。这个例子说明，AI输出的是可以运行和判定结果的程序代码。

### 3.3 Req2Test的一条数据具体长什么样

真实任务 `python-docx/features/doc-add-section.feature:16` 来自读写Word文档的python-docx项目。

Word文档中的“节”用于分别设置页面布局、页眉和页脚。这里要求已有一节且已有页眉页脚的文档，在新增一节后，新节继承前一节的页眉页脚。

该任务的原始需求为

```gherkin
Scenario: Document.add_section() adds a section that inherits headers and footers
    Given a single-section Document object with headers and footers as document
     When I execute section = document.add_section()
     Then section.header.is_linked_to_previous is True
      And section.even_page_header.is_linked_to_previous is True
      And section.first_page_header.is_linked_to_previous is True
      And section.footer.is_linked_to_previous is True
      And section.even_page_footer.is_linked_to_previous is True
      And section.first_page_footer.is_linked_to_previous is True
```

Given、When、Then分别表示“事先有什么条件”“执行什么操作”“应该出现什么结果”。上面这道题可以直接读成

- 已有一个带页眉页脚的单节文档。
- 执行新增一节的操作。
- 检查新节的普通页、偶数页、首页的页眉与页脚，都保持与前一节关联。

任务还会给出语言、框架、接口声明、允许保留的文件和输出目录。本例使用Python和behave框架，生成文件应放在 `features/steps/` 中。

### 3.4 Req2Test真实生成了什么

下面两段是该任务的原始输出节选。

```python
@when("I execute section = document.add_section()")
def when_add_section(context):
    context.section = context.document.add_section()
```

第一段把“新增一节”落实成程序调用。第二段把“页眉保持继承”落实成断言。其余文字步骤也要有对应代码，框架才能把完整场景执行起来。

## 五、指标怎么理解，结果是多少

### 5.1 先理解“变异测试”

为了检查测试有没有发现错误的能力，评测会准备软件的一些修改版本。例如故意把一个条件判断改错，或删掉一项必要操作。这样的版本称为“变异体”。

如果生成测试在正确软件上通过，而在这个改错的软件上报错，就说明测试识别到了这处变化，称为“杀死变异体”。如果改错后测试仍通过，就称该变异体“存活”。

变异测试提供了一组可重复的检错题目。指标的意义取决于具体变异池和官方筛选规则。

### 5.2 TestSuiteBench的两个主要指标

|指标|人话解释|本次结果|
|---|---|---:|
|Validity|把测试放到正确软件上，有多少测试实例能够通过|74.67%|
|Mutation Score|对于计分的修改版本，测试能识别其中多少|16.11%|

每个任务先各算自己的比例，再对165条任务取平均。Validity使用正确实现上的通过实例数除以测试实例总数。Mutation Score使用检出的变异数除以有效变异数，计分时采用在正确实现上通过的测试实例。

真实zoxide任务的计算如下。

- Validity为18 ÷ 19，约94.74%。
- Mutation Score为8 ÷ 39，约20.51%。

同一套测试可以有较高的正确实现通过率，同时漏掉较多变异。前一个指标回答“测试能否正常用于正确软件”，后一个指标回答“测试的检错能力怎样”。

## 六、第一项问题，需求里的业务状态不容易对应到正确操作

### 6.1 用已有页眉的Word文档解释

需求要求在“已经有页眉页脚”的文档里新增一节。生成测试的准备部分创建空文档，再逐个访问页眉页脚属性。关键代码如下，节选自原始生成文件。

```python
document = Document()
original_section = document.sections[0]
for name in (
    "header",
    "even_page_header",
    "first_page_header",
    "footer",
    "even_page_footer",
    "first_page_footer",
):
    getattr(original_section, name)
```

`getattr`在这里表示“取出这个属性对象”。python-docx可以先提供一个页眉代理对象，等后续需要实际内容时再建立对应定义。因此，这些访问没有完成需求要求的初始准备。

原生成代码的注释还声称这些操作已经建立了实际页眉页脚定义。代码和注释之间的差异，直接体现了对接口作用的误判。

### 6.2 实际发生了什么

1. 测试创建空文档。
2. 测试获取页眉页脚代理。
3. 测试真实执行 `document.add_section()`。
4. 测试检查6种继承标志。
5. 正确实现上测试通过。
6. 在一个删除页眉页脚引用清理操作的变异上，生成测试仍通过，参考测试检出错误。

对应变异ID为 `5d6e664690271921`。已有覆盖记录表明，参考测试走到了相关删除语句位置，生成测试未覆盖该位置。参考测试准备阶段直接加载带有页眉页脚的文档文件。

这说明本例需要重点处理**业务前提怎样建立**。后面的继承断言已经存在，前提准备却没有达到需求规定的状态。

### 6.3 为什么值得研究

真实项目中的“已有页眉”“订单已提交”“管理员能够看到”，往往需要特定的数据、调用顺序或读取入口才能实现。生成器必须弄清楚接口实际做了什么，才能把自然语言条件落实到程序里。

同类案例还包括CoreShop用本地数组和自建对象替代真实购物车到订单的转换，以及Sylius完成下单后只读取原订单对象，遗漏需求指定的管理员查询路径。两者分别反映生产操作选择和结果读取入口的问题。

在固定子集44条通过任务中，这一主题下已确认4条，分布在CoreShop、Coddy、python-docx、Sylius四个项目，占9.09%。这是当前通过任务中的静态复核比例。

**当前研究问题可以表述为，如何让生成测试准确使用项目接口，真正建立并检查需求要求的业务状态。**

## 七、第二项问题，断言容易漏掉“谁对应什么”以及具体限制

### 7.1 用请愿网站的真实数据解释

真实任务 `e-petitions/features/charlie_creates_a_petition.feature:6` 要求用户在创建请愿前，先搜索已有的相似请愿。

原始需求的预期结果表为

|请愿标题原文|对应签名人数|
|---|---|
|Do not remove rioters benefits|Total signatures 1,023|
|Rioters should loose benefits|Total signatures 835|

可以把标题分别理解为“不要取消暴乱者的福利”和“应该取消暴乱者的福利”。原始英文拼写按数据保留。

生成测试真实创建了数据、执行页面操作，并进入相似请愿结果页。随后用以下代码检查结果。

```ruby
Then("I should see the following similar petitions:") do |table|
  table.raw.each do |action, signatures|
    expect(page).to have_content(action)
    expect(page).to have_content(signatures)
  end
end
```

`have_content`表示页面中能找到这段文字。虽然循环里每次取出一组标题和签名数，两条检查都作用于整个页面。

### 7.2 它会漏掉什么

需求要求标题与人数成对对应。考虑一种用于解释断言的错误页面示意。

|页面显示的标题|错误地显示的人数|
|---|---:|
|Do not remove rioters benefits|835|
|Rioters should loose benefits|1,023|

两个标题仍然存在，两个数字也仍然存在，所以这段全页检查无法区分正确对应与人数交换。

这里的交换表用于展示原断言允许的错误结果。现有记录没有保存一次实际交换页面后的重跑结果。本例原生成测试确实执行通过，检出183个计分变异中的172个，剩余11个存活；当前已确认的检查缺口是对象与数值未绑定。

开发者参考测试在相应结果条目范围内检查标题及人数，从而保留“这条请愿对应这个签名数”的关系。

### 7.3 其他项目也出现了什么

- python-docx要求按文档顺序返回段落和表格，生成测试检查对象类型序列及段落文本，却没有检查三张表格各自的身份或内容次序。
- Kapua需求指定异常类型及消息，生成测试接受更宽泛的异常。
- Algorand需求指定空交易组的错误，生成测试捕获任意异常后仅检查异常存在。

在固定子集44条通过任务中，断言表达主题下确认4条，涉及e-petitions、python-docx、Kapua、Algorand四个项目，占9.09%。与第一项按主要缺口归类后，共8条独立任务、7个项目。

**当前研究问题可以表述为，如何把需求中的对象关系、顺序和异常限制，完整写进测试的判断条件。**

## 附录二、术语速查

|术语|含义|
|规格说明|写清楚软件应具备的功能、输入输出和规则的文件|
|需求场景|描述某个具体条件下，执行操作后应该得到什么结果|
|测试套件|组织在一起运行的一组测试|
|步骤定义|把Given/When/Then文字步骤落实成代码的函数|
|断言|自动判断实际结果是否符合预期的条件|
|参考测试|数据集提供的开发者测试，作为对照和评分依据|
|变异体|对软件做特定修改得到的版本，用于检查测试能否发现变化|
|杀死变异体|测试识别了某个变异，使对应测试失败|
|TH视图|生成时隐藏目标行为实现，保留官方允许的接口与上下文|
|计分分母|按照官方规则实际进入某项指标计算的任务或变异数量|
