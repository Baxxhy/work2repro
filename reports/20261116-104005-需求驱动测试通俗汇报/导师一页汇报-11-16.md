# 测试演化与需求驱动测试

2026年11月18日

## 一、测试演化

软件升级后，旧测试可能跑不过，或者还能跑却不再检查新行为。**测试演化**就是让测试随软件一起更新。

**复现的三种方法。** 我们给定代码改动和待更新的旧测试，看各方法怎么改。在 PRBench 和 Updates4J 上共完成766条任务。

|方法|怎么更新测试|PRBench 通过率|Updates4J 通过率|
|---|---|---:|---:|
|MuMuTestUp|根据没有测到的代码分支和没抓住的错误版本，补测试场景、改结果检查|87.7%|91.3%|
|TestUpdater|先找写测试需要的相关代码，再根据编译和运行报错反复修正|75.8%|77.4%|
|TestSyncer|先分析代码改了哪类内容、影响了哪些调用和依赖，再据此修改测试|37.0%|65.1%|

**项目级测试演化分两步。**

1. **识别演化。** 给 AI 整个项目和一次代码改动，让它找出哪些旧测试要改、哪些新行为还需要补测试。只看运行失败会漏掉**还能通过、但已经测不到新行为**的旧测试。
2. **执行演化。** 根据识别结果修改旧测试、补写新测试，交付一份测试补丁。评估时分别看位置找得准不准，以及更新后的测试能否通过、是否测到代码的改动。

**这个方向可以用 TEBench 做。** 它给 AI 一个 Java 项目和一次生产代码改动，要求从整个项目里定位并更新测试。共有10个项目、314条任务。原论文中，七组配置的识别 F1 为45.7%到49.4%。给定旧测试后怎么改，我们已有复现。项目级任务还要回答前面那一步，**一开始该改哪些测试、该补哪些测试？**

## 二、需求驱动测试

**动机。** AI 已经能按需求写程序，但程序能跑、现有测试能过，仍可能漏掉用户要求。我们直接从原始需求生成验收测试，检查交付的软件在规定场景下是否做对了。

|数据集|给 AI 什么，生成什么|复现结果|
|---|---|---|
|**TestSuiteBench（主）**|165份完整软件说明书，各生成一套测试|有效率 **74.67%**，变异得分 **16.11%**|
|Req2Test-Bench（补充）|8个项目、2,051个业务场景，各生成对应测试|Pass@1 29.73%，Mutation R 27.31%|

两个数据集都用 Codex CLI + GPT-6 Luna（medium）复现。有效率看生成测试在正确程序上能否通过，变异得分看它们能抓住多少故意引入的错误。

> [!NOTE]
> **变异体**就是故意把软件的一项行为改错的版本。测试在正确版本通过、在错误版本失败，就算抓住了这处错误。

### 三个痛点

以下代码均节选自实际生成的测试。

1. **生成测试难以覆盖能够暴露需求违例的关键场景。**

**点名搜两个文件，却测成了搜文件夹（TestSuiteBench / ast-grep）。** 规格要求，可以同时指定 `a.js` 和 `b.js` 搜索。实际生成代码如下，`tmp_path` 就是放这两个文件的文件夹。

```python
    (tmp_path / 'a.js').write_text('foo();\nbar();\n')
    (tmp_path / 'b.js').write_text('foo();')
    r = invoke(['run', '-p', 'foo()', '-l', 'js', '--files-with-matches', tmp_path], tmp_path)
    assert r.returncode == 0 and len(r.stdout.strip().splitlines()) == 2
```

**这段代码在做什么。** 前两行在同一个文件夹里创建 `a.js` 和 `b.js`，两个文件都有 `foo()`。第三行让程序去这个文件夹里搜。方括号里的 `tmp_path` 是唯一传给程序的搜索位置，括号末尾那个 `tmp_path` 只是指定命令在哪个目录运行。最后一行只要求命令运行成功，输出有两行。

**问题在哪。** “搜一个文件夹里的两个文件”可以输出两行，但需求还要求“分别指定两个路径时都要搜”。这段代码没有分别传入 `a.js` 和 `b.js`，所以即使程序有“忽略第二个路径”的错误，也无法靠这个用例发现。

2. **生成测试的断言难以保留需求中的关键约束。**

**找到了，却没检查找到什么（TestSuiteBench / ripgrep）。** 像在文档里搜关键词，结果应该告诉用户是哪个文件、第几行、匹配了什么。此例实际搜索的是 `hit`。

```python
    f=tmp_path/'x'; f.write_text('a hit\nno\n')
    p=run(['--json','hit',f]); assert p.returncode==0 and not p.stderr
    objs=[json.loads(x) for x in p.stdout.splitlines()]
    assert [x['type'] for x in objs]==['begin','match','end','summary']
```

**这段代码在做什么。** 第一行写了一个两行的文件，只有第一行含有 `hit`。第二行运行搜索，第三行把程序返回的每条消息读出来。最后一行的 `x['type']` 只拿每条消息的类别，例如 `match` 就是“找到了”。

**问题在哪。** 需求要检查的是“在哪个文件、第几行、找到了什么”。代码只确认有一条叫“找到了”的消息，里面写了什么一概没读。我们把匹配详情全部去掉，只留下四种消息的类别，原测试仍然通过。

<details>
<summary>补充对照：请愿网站的签名数（Req2Test）</summary>

需求表规定第一条请愿显示1,023人、第二条显示835人。原测试逐行读表，却分别到整个网页里找标题和人数。

```ruby
    expect(page).to have_content(action)
    expect(page).to have_content(signatures)
```

第一行在整个网页（`page`）上找标题（`action`），第二行在同一整个网页上找人数（`signatures`）。**问题在哪。** 需求要查一条记录里的标题和人数是否正确配对，代码只查二者是否分别出现。按代码推导，即使两条请愿的数字对调，两行也能通过。

3. **生成阶段缺少能够揭示需求违例漏检的有效反馈。**

**使用说明缺了一项，测试仍通过（TestSuiteBench / rnr）。** 批量改文件名的工具在用户没输入命令时，要显示完整的帮助。Agent 实际生成的是下面这两行检查。

```python
    p = run([], work)
    assert p.returncode == 2 and p.stdout == '' and p.stderr.startswith('RnR is a command-line tool')
```

**这段代码在做什么。** `run([])` 表示直接启动工具，什么命令都不输入。下一行要求程序报告“用法错误”，常规输出为空，并且帮助文本以固定的一句话开头。这里的 `startswith` 只比较开头。

**问题在哪。** 需求要求列出完整帮助，但这条检查读不到后面有哪些命令。提交后，官方评测既跑了完整版本，也跑了删掉 `to-ascii` 说明的版本，两边都通过，因为开头没有变化。Agent 在生成时做的语法检查和报告检查也看不出这一点。即使提前给它完整版本的通过结果，它仍然缺少“删掉一项也过”的反馈。
