# 测试演化与需求驱动测试研究进展

2026年11月17日更新

## 一、测试演化

**研究任务。** 软件更新后，自动修改旧测试，使它适应新版本，并继续发现功能错误。

**已完成工作。** 复现三种方法，统一使用GPT-6 Luna、medium，在PRBench和Updates4J共766条任务上完成实验。

- **MuMuTestUp**结合执行错误、覆盖率和变异测试反馈，多轮更新测试。
- **TestUpdater**按需收集相关代码，再根据编译和运行错误修正测试。
- **TestSyncer**分析代码变化类型、依赖和调用位置，引导模型更新测试。

|数据集|MuMuTestUp通过率|TestUpdater通过率|TestSyncer通过率|
|---|---:|---:|---:|
|PRBench，571条|87.7%|75.8%|37.0%|
|Updates4J，195条|91.3%|77.4%|65.1%|

**方向调整。** 给定旧测试后的更新已有较高通过率，我们考虑的上下文补充、执行反馈等思路也已有工作采用，目前尚未找到明确切入点。该方向正在向项目级发展，例如TEBench要求从整个仓库中找到需要修改或新增的测试，再完成更新。我们将研究重点转向根据用户需求生成测试，验证新开发功能是否符合预期。

## 二、需求驱动测试

**研究动机。** Coding Agent已经能够根据自然语言需求开发软件，但程序能运行、测试能通过，仍可能没有满足用户要求。希望直接根据原始需求生成测试，用来验收Coding Agent交付的软件。

**两个Benchmark的任务。**

|数据集|输入|输出|
|---|---|---|
|TestSuiteBench|一份Markdown格式的完整软件功能说明，规定输入、输出和异常规则|一整套可执行测试|
|Req2Test-Bench|一个“已有条件 → 执行操作 → 预期结果”的具体场景，以及允许查看的项目接口和上下文|该场景对应的测试步骤代码|

**复现配置与结果。** 使用Codex CLI + GPT-6 Luna、medium。

|数据集|规模|主要指标|
|---|---|---|
|TestSuiteBench|165条|Validity 74.67%，Mutation Score 16.11%|
|Req2Test-Bench|固定160条，计分159条|Pass@1 27.57%，KillComplete@1 12.53%|

Validity和Pass@1反映测试在正确软件上能否通过；Mutation Score反映能检出多少故意引入的错误；KillComplete要求任务通过且检出全部计分变异。Req2Test指标按官方规则对项目等权平均。

### 从真实测试中发现的三个问题

**1. 一个功能测过了，不代表其中的要求都测到了。**

**真实案例：TestSuiteBench，目录管理工具zoxide。** 数据集用一份`spec.md`说明软件规则，其中规定：同一个分数参数不能重复输入。

- **用户要求：** 添加目录时，分数只能填一次；重复填写必须报错。
- **生成测试：** 检查了“不填分数”“分数不是数字”，却没有检查“分数填了两次”。
- **实际后果：** 官方变异版本把规则改成“重复填写也接受，采用最后一个分数”，测试没有发现。

**痛点：Agent围绕功能写了测试，却没有把功能中的每项具体规则落实为用例。**

**2. 测试看起来完成了业务操作，实际绕过了真实软件。**

**真实案例：Req2Test-Bench，CoreShop购物下单。** 数据集在`.feature`文件中，用“已有条件、执行操作、预期结果”描述场景。下面为原场景的中文概括。

- **用户要求：** 购物车加入一件T恤，使用优惠券、填写地址，再生成订单；订单中应有一件商品。
- **生成测试：** 没有调用真实的购物车转订单服务，而是自己创建数组放入T恤，再包装成“订单”，检查商品数量为一。
- **实际后果：** 测试通过了，但它检查的是自己造的数据，不能证明真实下单功能正常。该任务200个计分变异均未检出。

**痛点：Agent遇到项目集成困难后，用简化逻辑替代了本来需要验证的业务过程。** 生成轨迹记录了它选择本地替代逻辑的过程；200个变异未检出是任务结果，不表示每个都已归因到这一个原因。

**3. 操作确实执行了，但检查方式让错误结果也能通过。**

**真实案例：Req2Test-Bench，e-petitions请愿网站。** 原始需求同样保存在`.feature`场景中。

- **用户要求：** 页面上两项请愿应分别显示各自的标题，以及对应的1,023和835个支持者。
- **生成测试：** 在整个页面中分别查找两个标题和两个数字，没有检查“哪个数字属于哪项请愿”。
- **遗漏的错误：** 即使两项请愿的人数显示反了，标题和数字仍然全部存在，这组检查也会接受。

**痛点：需求要求检查“标题与人数的对应关系”，生成测试却只检查“标题和人数是否出现”。** 人数交换是根据生成代码确认的检查缺口，本轮没有重新执行交换实验。

### 当前证据与下一步

Req2Test的44条通过任务中，已确认第2类问题4条、第3类业务约束问题5条，重叠1条，**合计8条，占18.18%，涉及7个项目**。这说明问题会出现在已经通过的测试里。第1类在TestSuiteBench已有真实案例，完整发生比例尚待逐任务核查；目前不能说三类问题都高频。

下一步继续利用已有需求、生成代码和执行轨迹，统计每类问题的比例，区分“漏了场景”“绕过真实业务”“结果检查失真”。结合TELPA的对象构造与依赖分析、TOGLL的断言生成研究，判断已有方法还缺少什么，再确定研究切入点。
