# 测试演化与需求驱动测试研究进展

2026年11月16日 · 导师精简汇报

## 一、测试演化——软件更新后，怎样自动更新旧测试

**动机与任务。** 软件更新会改变接口、依赖或功能。输入代码新旧版本、旧测试及相关变更，输出能用于新版本的更新后测试，希望减少人工维护并保留有效检查。

**已完成。** 复现MuMuTestUp、TestUpdater、TestSyncer，统一使用GPT-6 Luna、medium，保留各方法自身流程。两个数据集共766条任务，三种方法共2,298条生成记录。

|数据集|MuMuTestUp通过率|TestUpdater通过率|TestSyncer通过率|
|---|---:|---:|---:|
|PRBench，571条|87.7%|75.8%|37.0%|
|Updates4J，195条|91.3%|77.4%|65.1%|

**真实代码例子。** PRBench的cucumber-reporting第47条，开发者更新了测试读取内部状态的辅助调用。

```java
// 旧测试使用的调用
ReflectionUtility.getField(page, "context", VelocityContext.class);
// 开发者更新后的调用
Deencapsulation.getField(page, "context");
```

三种方法在这条任务上均编译失败，TestSyncer日志明确报告旧类`ReflectionUtility`无法解析，说明测试辅助依赖的更新仍有遗漏。

### 为什么暂缓测试演化，转向需求驱动测试

复现后发现，最初考虑的上下文收集、执行反馈和断言增强，已有TestUpdater、MuMuTestUp等工作进行处理。当前找到的辅助类迁移等失败，还需要进一步证明能形成独立、可推广的研究问题，继续开发方法的依据尚不充分。

同时，测试演化依赖旧测试和代码变更。我们更关注AI根据需求开发新功能时，如何发现实现中的业务错误，这时可能还没有可供更新的旧测试。因此，将当前研究重点转到“直接根据需求生成测试”，围绕需求是否真正得到验证寻找切入点。

## 二、需求驱动测试——根据用户要求生成测试，发现功能bug

**动机。** 软件能够运行，业务结果仍可能做错。让AI根据需求编写测试，自动执行操作并判断结果是否符合要求。本次使用 **Codex CLI + GPT-6 Luna，medium**。

### 数据集具体给什么

|数据集|真实输入例子|AI输出|本次规模|
|---|---|---|---|
|TestSuiteBench|整个软件的功能要求，称为“规格说明”。例如zoxide规定目录怎样添加、查询、删除，以及输错参数怎样报错|调用软件并检查结果的一整套测试|全部165条|
|Req2Test|一个具体场景及允许访问的项目上下文。例如“已有页眉的Word文档新增一节后，应继承原页眉”|准备文档、新增一节、检查继承的步骤代码|固定160条，计分159条|

### 复现结果

- **TestSuiteBench**的Validity为 **74.67%**，表示正确软件上的测试通过比例；Mutation Score为 **16.11%**，表示对计分的故意修改版本的检出比例。
- **Req2Test**的Pass@1为 **27.57%**，表示任务通过率；KillComplete@1为 **12.53%**，表示通过且检出全部计分变异的任务比例。共44条通过，其中20条达到KillComplete，百分比按官方项目等权计算。

### 原始数据与变异来自哪里

以下每项问题各有一个TestSuiteBench案例和一个Req2Test案例，共四个。英文块直接摘自保存的原始任务，随后给出中文解释。

- **TestSuiteBench**提供整份软件规格。下面摘出与缺口相关的条款，完整规格随文档保存在“原始案例与变异”目录。变异来自本次锁定的官方`eth-sri/tsb-mutants`数据包，改变待测软件的行为。
- **Req2Test**提供具体Given/When/Then场景。变异来自已经下载的官方项目评测包，修改生产代码中的特定语句。下列两个变异都有开发者参考测试检出、生成测试通过的原始记录。

### 问题① 需求规定了条件，生成测试却没有把条件落实完整

#### 例1 · TestSuiteBench · zoxide

**任务ID**为`ajeetdsouza__zoxide.67ca1bc`。输入是命令行目录管理软件的完整规格。

**原始规格，Spec 1与Spec 2节选**

```text
Repeated scalar options such as `--score` and `--from` are usage errors.
Argument parsing errors return 2 and use the clap-style form shown below.
```

**中文意思。** 同一次命令重复填写`--score`等单值参数，应报参数错误并返回状态码2。

**生成测试实际检查什么。** 原代码列出的参数错误输入如下，省略参数化装饰器的其他设置。

```python
[("add",), ("init",), ("import",),
 ("add", "--score", "x", "/tmp")]
```

它检查了缺少参数、分数不是数字等情况。核对整个生成套件后，没有找到同一命令重复传入`--score`的用例。

**具体变异。** 官方变异`repo_1`，对应原始分配ID`repo_2`，在`src/cmd/cmd.rs`的`Add`命令定义中增加

```rust
args_override_self = true,
```

结果变成重复参数可以接受，后一个值覆盖前一个值。规格要求的“重复参数必须报错”被破坏。

**执行结果。** 正确版本上18/19个测试实例通过，整个套件检出8/39个计分变异。上述重复参数变异存活，已有有效测试没有检出它。**这例遗漏了触发错误所需的输入条件。**

#### 例2 · Req2Test-Bench · python-docx

**任务ID**为`python-docx/features/doc-add-section.feature:16`。输入是Word文档新增节的具体场景。

**原始需求**

```gherkin
Scenario: Document.add_section() adds a section that inherits headers and footers
    Given a single-section Document object with headers and footers as document
     When I execute section = document.add_section()
     Then section.header.is_linked_to_previous is True
      And section.even_page_header.is_linked_to_previous is True
      And section.first_page_header.is_linked_to_previous is True
      And section.footer.is_linked_to_previous is True
      And section.even_page_footer.is_linked_to_previous is True
      And section.first_page_footer.is_linked_to_previous is True
```

**中文意思。** 已有一个带页眉页脚的单节文档，新增一节后，新节的普通页、偶数页和首页的页眉页脚都应继承前一节。

**生成测试关键代码。** 以下合并展示原准备和检查语句，省略函数包装。

```python
original_section = document.sections[0]
for name in ("header", "even_page_header", "first_page_header",
             "footer", "even_page_footer", "first_page_footer"):
    getattr(original_section, name)
context.section = context.document.add_section()
assert context.section.header.is_linked_to_previous is True
```

获取属性只得到了代理对象，没有建立实际页眉页脚定义。需求中的“已有页眉页脚”没有准备到位。

**具体变异。** 官方变异`5d6e664690271921`修改`src/docx/oxml/document.py`第69行。

```diff
- sentinel_sectPr.remove(hdrftr_ref)
+ pass
```

它删掉了新增节时清理页眉页脚引用的操作。参考测试加载带实际页眉页脚的文档，覆盖该语句并检出变异；生成测试未覆盖该语句，在变异上仍通过。

**执行结果。** 正确版本上通过，检出112/113个计分变异，上述变异存活。**这例写了继承断言，但初始文档状态没有满足需求。**

**两例共同说明。** 需求中的输入条件或初始状态，可能在生成测试时丢失。zoxide表现为没有生成对应异常输入，python-docx表现为错误地准备初始状态。两者的具体成因需要分别调查。

### 问题② 测试执行了操作，但断言只检查了部分要求

#### 例3 · TestSuiteBench · rnr

**任务ID**为`ismaelgv__rnr.fc0733b`。输入是批量重命名工具的完整规格。

**原始规格，Spec 24及Spec 2节选**

```text
Running with no command prints the complete main help to stderr and no stdout.

Commands:
  regex      Rename files and directories using a regular expression
  from-file  Read operations from a dump file
  to-ascii   Replace file name UTF-8 chars with ASCII chars representation
  help       Print this message or the help of the given subcommand(s)
```

**中文意思。** 不输入命令时，程序必须在错误输出中显示完整帮助，包括这些命令及说明。

**生成测试原始代码节选**

```python
p = run([], work)
assert p.returncode == 2 and p.stdout == '' and p.stderr.startswith('RnR is a command-line tool')
```

测试实际执行了无参数启动，但只核对退出码、输出位置和帮助文字的开头，没有检查完整命令列表。

**具体变异。** 官方`repo_1`对应分配ID`repo_1`。其`src/mutant.rs`在无参数启动时调用

```rust
render_help(&args, Some("to-ascii"), None)
```

`render_help`会过滤包含`to-ascii`的行。因此这条命令说明消失，帮助文字开头仍保持原样。官方差分包含多个可选分支，本例按`repo_1`选择生效的分支分析。

**执行结果。** 上面这个测试在正确版本和变异版本上都通过。整个套件正确版本通过42/45个测试实例，检出11/72个计分变异，该变异存活。**需求要求完整内容，断言只查了开头。**

#### 例4 · Req2Test-Bench · Kapua

**任务ID**为`kapua/service/account/test/src/test/resources/features/AccountService.feature:120`。输入是删除不存在账号的具体场景。

**原始需求**

```gherkin
Scenario: Delete nonexisting account
  Try to delete an account with a a random Id. The operation should fail and an exception
  should be thrown.

    Given I expect the exception "KapuaEntityNotFoundException" with the text "The entity of type account with id/name"
    When I delete a random account
    Then An exception was thrown
```

**中文意思。** 删除随机ID的不存在账号，应抛出`KapuaEntityNotFoundException`，并且异常消息包含“The entity of type account with id/name”。

**生成测试原始代码节选**

```java
} catch (KapuaException e) {
    stepData.put(EXCEPTION_CAUGHT, true);
    return;
}
```

它执行了删除操作，但捕获宽泛的`KapuaException`后只标记“发生过异常”，没有核验指定类型和消息。

**具体变异。** 官方变异`f9696266b289835c`修改`service/api/src/main/java/org/eclipse/kapua/ExceptionMessageUtils.java`第70行。

```diff
- return MessageFormat.format(pattern, args);
+ return null;
```

异常消息被改成空值，需求指定的消息要求遭到破坏。

**执行结果。** 生成测试在正确版本及该变异上均通过，开发者参考测试检出该变异。任务整体检出22/43个计分变异。原记录存在重复计数异常，本例已按唯一变异ID核对上述执行状态。**需求指定异常内容，生成测试只确认有异常。**

**两例共同说明。** 调用了正确操作后，测试仍可能接受过宽的结果范围。rnr只检查文本开头，Kapua只检查异常存在。研究重点是怎样把需求中的具体限制完整表达成断言。

### 当前分析进度

两个数据集中都找到需求条件落实不完整、断言检查不完整的具体案例。Req2Test的44条通过任务中已确认8条业务缺口，涉及7个项目，占18.18%；TSB已有6条定向分析，本稿展示其中两例，全部165条的语义发生比例尚未统计完成。

接下来分别核对这些案例的生成记录，调查信息遗漏、接口使用错误及检查条件弱化的原因。原始任务、完整规格、生成代码、变异差分和对应执行记录保存在同目录的“原始案例与变异”文件夹。本轮没有新增生成或评测。

## 三、下一步工作计划

1. **对照相近研究，明确已有方法能解决到哪里。** 重点阅读TELPA（TOSEM 2025）的复杂对象准备与调用依赖分析，以及TOGLL（ICSE 2025）、ChatAssert（TSE 2025）的断言生成与修正，比较它们的输入条件、检查范围和实验设计。
2. **继续利用已有结果验证问题。** 在两个数据集中补充同类失败案例和成功对照，结合需求、生成记录及变异结果，区分需求条件被遗漏、接口使用错误、断言约束被弱化，并分别统计。
3. **优先从“需求明确写出的限制，为什么没有进入断言”入手。** 当前这一问题较容易建立需求、代码和漏检结果之间的对应关系，也有相关工作可作比较。先检查具体异常、对象对应关系等场景，判断已有方法还缺少什么，再确定研究方案。

当前对两个主题的判断有所区别。需求条件遗漏包含“少写一个输入”和“错误准备业务状态”等不同情况，仍需分别查原因；断言约束遗漏更适合优先开展可控对照。研究重点将随新增证据调整。
