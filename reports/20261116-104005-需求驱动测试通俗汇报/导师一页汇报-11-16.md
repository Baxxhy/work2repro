# 测试演化与需求驱动测试研究进展

2026年11月18日更新

## 一、测试演化

**研究任务。** 软件更新后，自动修改旧测试，使它适应新版本，并继续发现功能错误。

**已完成工作。** 复现三种方法，统一使用GPT-6 Luna、medium，在PRBench和Updates4J共766条任务上完成实验。

- **MuMuTestUp**结合执行错误、覆盖率和变异测试反馈，多轮更新测试。
- **TestUpdater**按需收集相关代码，再根据编译和运行错误修正测试。
- **TestSyncer**分析代码变化类型、依赖和调用位置，引导模型更新测试。

|数据集|MuMuTestUp通过率|TestUpdater通过率|TestSyncer通过率|
|---|---:|---:|---:|
|PRBench，571条|87.7%|75.8%|37.0%|
|Updates4J，195条|91.3%|77.4%|65.1%|

**方向调整。** 给定旧测试后的更新已有较高通过率，我们考虑的上下文补充、执行反馈等思路也已有工作采用，目前尚未找到明确切入点。该方向正在向项目级发展，例如TEBench要求从整个仓库中找到需要修改或新增的测试，再完成更新。我们将研究重点转向根据用户需求生成测试，验证新开发功能是否符合预期。

## 二、需求驱动测试

**研究动机。** Coding Agent已经能够根据自然语言需求开发软件，但程序能运行、测试能通过，仍可能没有满足用户要求。希望直接根据原始需求生成测试，用来验收Coding Agent交付的软件。

**两个Benchmark的数据特点。** 两者都根据英文自然语言生成测试，但任务粒度和可见信息不同。

|特点|TestSuiteBench|Req2Test-Bench|
|---|---|---|
|任务规模|165个命令行应用，全部复现|8个项目，eval共2,051条，已有全量评测结果|
|输入形式|Markdown规格文件`spec.md`，按章节规定命令、参数、输出、异常和状态规则|Gherkin格式`.feature`文件，包含Feature、Background和目标Scenario，另提供接口声明及允许的仓库上下文|
|输入粒度|整个应用，规格中位数约5,635词、23节|一个具体场景；步骤明确，但对象初始化、共享状态和服务依赖仍需结合项目确定|
|项目语言|Rust、Go、C/C++|Java、PHP、Python、Ruby、Go|
|生成产物|整套黑盒测试；本次产物为Python/pytest测试和`run.sh`|项目原生测试步骤：Java/Cucumber、PHP/Behat、Python/behave、Ruby/Cucumber、Go/Godog|
|生成可见范围|默认仅规格，不提供生产源码或参考可执行程序|隐藏目标实现，保留接口声明及允许的项目上下文；参考测试不向Agent开放|

**输入实际形态。** TestSuiteBench的zoxide规格中有规则：`Repeated scalar options such as --score and --from are usage errors.`，即同一个分数或导入格式参数重复填写时必须报错。它是长规格中的一项规则，不是一道独立测试题。

Req2Test的CoreShop输入则是一个具体业务场景，例如以下原始步骤节选：

```gherkin
Scenario: Create a new order and add a product
  Given I add the product "T-Shirt" to my cart
  And I apply the voucher code "asdf" to my cart
  # 此处省略原始配送与账单地址步骤
  And I create an order from my cart
  Then there should be one product in my order
```

因此，“需求已经写清操作顺序”仍不等于“测试实现简单”：Agent还要把自然语言步骤接到项目中的真实对象、服务和检查入口。上述被测软件语言与测试代码语言并不总是相同，例如Rust程序可以用Python通过命令行测试。

**复现配置与结果。** 使用Codex CLI + GPT-6 Luna、medium。

|数据集|规模|主要指标|
|---|---|---|
|TestSuiteBench|165条|Validity 74.67%，Mutation Score 16.11%|
|Req2Test-Bench|2,051条，协议人口2,037条|Pass@1 29.73%，Mutation R 27.31%，KillComplete@1 13.33%|

Validity和Pass@1反映测试在正确软件上能否通过；Mutation Score反映能检出多少故意引入的错误；Req2Test的Mutation R衡量对参考测试已检出变异的召回，KillComplete要求任务通过且检出全部计分变异。Req2Test指标按官方规则对项目等权平均。

### 研究目标与三个挑战

**研究目标。** 提高需求生成测试对错误行为的检出能力，同时保持它在正确实现上的有效性。我们逐条复核了Req2Test固定子集中的44条通过任务，确认8条存在业务步骤、状态或结果判定缺口（18.18%，涉及7个项目）。TestSuiteBench已有对应的变异执行案例，165条任务的漏检机制比例仍待统计。

#### 1. 生成测试难以覆盖能够暴露需求违例的关键场景

**具体难点。** 需要从需求中识别哪些条件会改变预期行为，再把它们变成实际的测试输入、准备状态和真实调用。

- **TestSuiteBench / zoxide。** Markdown规格规定重复传入 `--score` 必须报错。Agent读取了规格，最终测试只覆盖缺参数和非法参数等情况。具体漏检原因是测试输入中没有两次 `--score`，因此未检出“接受重复参数并采用最后一个值”的官方变异。该套件整体检出8/39个变异。
- **Req2Test / CoreShop。** Gherkin场景要求从已使用优惠券的购物车创建订单。Agent搜索接口契约和项目代码后，采用本地数组和匿名对象构造订单。数量断言读取的是测试自己放进数组的商品，真实下单服务没有被调用。这个任务通过，整体检出0/200个变异。

两例都缺少能暴露错误的执行条件。zoxide缺少特定输入组合，CoreShop缺少真实的业务操作。

#### 2. 生成测试的断言难以保留需求中的关键约束

**具体难点。** 测试要从合适的位置读取结果，并检查需求规定的对象关系、范围和完整性。

- **Req2Test / e-petitions。** 需求要求两条请愿分别显示1,023和835个签名。生成测试用以下两行在整页分别找标题和人数。

```ruby
expect(page).to have_content(action)
expect(page).to have_content(signatures)
```

  具体缺口是两次检查都针对整个页面，因此没有核对标题和人数是否属于同一条请愿。按该断言，即使页面互换两条请愿的人数，检查也会通过。互换是从代码推导的反例。该任务官方评测通过，整体检出172/183个变异。

- **TestSuiteBench / rnr。** 规格要求无参数时输出完整帮助。生成测试检查了退出状态和帮助前缀。官方变异删除了 `to-ascii` 的命令说明，帮助开头仍然相同，这条测试在参考程序和变异程序上都通过。

#### 3. 生成阶段缺少能够揭示需求违例漏检的有效反馈

**具体难点。** 检查能否编译或运行，只能回答测试在当前条件下发生了什么。要定位漏检，还需要知道哪种错误仍会被接受，以及该补输入条件、真实调用、观察范围，还是结果检查。

**案例与证据。** 以e-petitions为例，即使测试在正确页面上通过，这次运行也无法揭示两条请愿的签名数互换后仍会通过。TestSuiteBench的额外对照中，向Sol提供参考可执行程序后，有效率从94.4%升到98.4%，变异得分只从37.7%变为38.1%。两套基准的官方变异评测都在提交后进行，因此生成阶段需要能指出具体漏检的信号，才能决定该补场景还是改断言。

**下一步。** 先在已确认的案例上分开核对场景和判据，记录每处调整能多检出哪种错误。再用同模型、同预算的实验，验证生成阶段的漏检诊断能否提高官方变异检出率，并同时检查参考实现上的有效率。前两条已有代码及变异执行证据。第三条已有轨迹和公开对照支持，诊断反馈的改进效果待验证。
