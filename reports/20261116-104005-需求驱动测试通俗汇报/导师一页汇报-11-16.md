# 测试演化与需求驱动测试研究进展

2026年11月18日更新

> [!NOTE]
> **开场可以这样讲。** AI 已经能按需求写程序。现在我想让 AI 再按同一份需求写一套验收测试，检查交付的软件做得对不对。实验发现，不少测试在正确程序上能通过，但把程序的某项行为故意改错以后，测试还是通过。我们研究怎么让测试把这些错误抓出来。

## 一、测试演化

软件升级时，先找出哪些旧测试受影响，再修改这些测试，使它们能在新版上运行并继续检查功能。我用 GPT-6 Luna（medium）复现了三种测试更新方法，共766条任务。

|数据集|MuMuTestUp|TestUpdater|TestSyncer|
|---|---:|---:|---:|
|PRBench，571条|87.7%|75.8%|37.0%|
|Updates4J，195条|91.3%|77.4%|65.1%|

表中是更新后的测试通过率。MuMuTestUp 结合执行、覆盖和变异反馈，TestUpdater 按需看代码并修正运行错误，TestSyncer 根据代码变更及其影响更新测试。给定旧测试的任务已有方法在两个数据集上接近九成通过。例如，TEBench 已把问题扩展到先从整个项目中找出哪些测试要改，再更新这些测试。我目前转向一个更贴近 AI 开发新功能的问题：当手头有用户需求，需要建立验收测试时，AI 能不能写出真能抓错的测试？

## 二、需求驱动测试

### 实验给 AI 什么，怎么判断测试有没有用

|数据集|给 AI 的材料|AI 交付什么|
|---|---|---|
|TestSuiteBench，165个命令行应用|一整份 Markdown 软件说明书。它写明命令怎样用、应该输出什么、什么情况下必须报错。生成时只有规格|一整套可以调用软件的测试|
|Req2Test-Bench，8个项目、2,051个场景|一段 Gherkin 需求，写明“先准备什么、再做什么、最后应看到什么”。另给部分仓库代码和接口，隐藏目标实现|能在原项目中执行这段需求的测试代码|

例如，同一条“重复填写参数要报错”可以是软件说明书里的一项规则。“商品加进购物车、用优惠券、创建订单”则是一个完整的需求场景。TestSuiteBench 的被测应用主要用 Rust、Go 或 C/C++ 编写，本次生成的是 Python 测试。Req2Test 则按原项目的 Java、PHP、Python、Ruby 或 Go 测试框架交付。

**怎么评。** 我们用同一个 Codex Agent 和 GPT-6 Luna（medium）生成测试。交卷后，评测器先在参考程序上运行，再换成故意改错的版本运行。每个这样的错误版本叫一个**变异体**。同一个测试在参考程序上通过、在某个计分变异体上失败，就称为检出了这个变异。比如，规格要求重复填写分数参数要报错，评测就用一个“重复填写也接受”的版本来检验测试能不能抓到它。

|数据集|参考程序上的表现|检出错误版本的表现|
|---|---|---|
|TestSuiteBench|测试有效率 74.67%|变异得分 16.11%|
|Req2Test-Bench|Pass@1 29.73%|Mutation R 27.31%，KillComplete@1 13.33%|

TestSuiteBench 的有效率按测试项看。Req2Test 的 Pass@1 按任务看，Mutation R 衡量参考测试能抓到的变异中生成测试找回了多少，KillComplete@1 衡量一次生成就通过且抓全计分变异的任务比例。两个数据集各用自己的官方口径。

### 三个痛点

在 Req2Test 固定子集的44条通过任务中，逐条核对发现8条存在业务步骤、状态或结果检查缺口，占18.18%，涉及7个项目。下面三个例子说明问题是怎么发生的。

#### 1. 生成测试难以覆盖能够暴露需求违例的关键场景

**例子。** zoxide 是个命令行工具。说明书要求，同一个分数参数写两次，程序必须报错。AI 写了一个“分数填字母”的用例，却没有把分数参数写两次。

> [!WARNING]
> **为什么会漏检。** “分数不是数字”和“参数写了两次”是两种不同的情况。评测把程序改成“参数写两次就用最后一个值”，但这套测试从未传过两次，所以抓不到这个错误。

<details>
<summary>展开原始需求、生成代码和 Agent 的操作</summary>

**原始规格。** Repeated scalar options such as `--score` and `--from` are usage errors.

**实际生成代码。** 参数列表重新排版，省略显示名称。

```python
@pytest.mark.parametrize("args", [
    ("add",), ("init",), ("import",),
    ("add", "--score", "x", "/tmp"),
])
def test_usage_errors_are_status_two(ctx, args):
    *_, call = ctx
    r = call(*args)
    assert r.returncode == 2 and not r.stdout and r.stderr.startswith(b"error:")
```

**执行与结果。** Agent 读规格，写了测试和运行脚本，并检查 Python 语法。提交后的官方评测发现，加入 `args_override_self = true` 的变异未被检出，套件整体检出8/39个变异。

</details>

<details>
<summary>补充例子：商城测试没有走真实的下单流程</summary>

**原始需求。** 以下节选省略地址步骤。

```gherkin
Given I add the product "T-Shirt" to my cart
And I apply the voucher code "asdf" to my cart
And I create an order from my cart
Then there should be one product in my order
```

**实际生成代码。** 测试把商品存进自己的数组，再用该数组构造了一个临时订单对象。

```php
    public function createOrderFromCart(): void
    {
        $this->order = new class($this->items) {
            public function __construct(private array $items)
            {
            }

            public function getItems(): ?array
            {
                return $this->items;
            }
        };
    }
```

**执行与结果。** Agent 搜索接口和准备代码后，采用内存里的订单对象，用 `php -l` 检查语法。最后的 `Assert::count($this->order->getItems(), 1)` 数的是测试自己放进数组的商品，真实下单服务没有执行。任务通过，检出0/200个计分变异。

</details>

#### 2. 生成测试的断言难以保留需求中的关键约束

**例子。** 请愿网站要显示两个标题及各自的签名数。原始数据中，第一条请愿有1,023个签名，第二条有835个。AI 在整个网页上找标题，再在整个网页上找数字。

> [!WARNING]
> **为什么会漏检。** 如果网站把两条请愿的签名数写反，两个数字仍然都在网页上。测试始终在整页查找，所以识别不了数字写在了哪一条下面。签名数互换是根据实际代码推导的反例。

<details>
<summary>展开原始需求、生成代码和 Agent 的操作</summary>

**原始需求。** 每个标题与签名数在需求表的同一行。

```gherkin
Then I should see the following similar petitions:
    | Do not remove rioters benefits | Total signatures 1,023 |
    | Rioters should loose benefits  | Total signatures 835   |
```

**实际生成代码。** `action` 是标题，`signatures` 是签名数，`page` 是整个页面。

```ruby
Then("I should see the following similar petitions:") do |table|
  table.raw.each do |action, signatures|
    expect(page).to have_content(action)
    expect(page).to have_content(signatures)
  end
end
```

**执行与结果。** Agent 读取场景、页面选择器和测试数据构造代码。它两次运行 Cucumber，都在隐藏的 `build_petition_creator` 方法处中断。提交后，官方环境运行通过，整体检出172/183个变异。

</details>

#### 3. 生成阶段缺少能够揭示需求违例漏检的有效反馈

**例子。** 文件重命名工具 rnr 要求不传命令时显示完整帮助。AI 写的测试只看帮助的第一行开头。官方评测时，同一条测试在**正确版本上通过，删掉一项命令说明的错误版本上也通过**。

> [!WARNING]
> **为什么会漏检。** 删掉的是后面的命令说明，第一行开头没变。即使交卷前能在正确版本上跑通，Agent 看到一个“通过”，仍然不知道命令说明缺一项也能通过。我们需要的反馈要能具体指出，测试漏掉的是对命令列表的检查。

<details>
<summary>展开原始需求、生成代码和前后执行记录</summary>

**原始规格。** Running with no command prints the complete main help to stderr and no stdout. 完整帮助包括 `to-ascii` 的说明。

**实际生成代码。** `run([])` 表示不传命令，`startswith` 只检查错误输出的开头。

```python
def test_missing_and_unknown_commands(work):
    p = run([], work)
    assert p.returncode == 2 and p.stdout == '' and p.stderr.startswith('RnR is a command-line tool')
```

|阶段|实际执行记录|
|---|---|
|Agent 写测试时|读取规格，语法检查成功。尝试运行测试入口，但生成环境没有参考程序。|
|提交后评测参考程序|检查通过。|
|提交后评测官方变异 `repo_1`|无命令帮助中的 `to-ascii` 说明被删除，检查仍通过。|

TestSuiteBench 原论文还有一个对照。让 Sol 在生成时使用参考程序，有效率从94.4%升到98.4%，变异得分从37.7%变为38.1%。第三项的研究问题是，这类漏检能否在提交前被发现并定位。

</details>


### 下一步

先用已有案例验证，补上关键输入或实际业务调用能不能让错误暴露。再保持输入和操作相同，看看改进结果检查后能不能把错误抓住。再比较加入漏检反馈前后，测试能否抓到更多独立评测的错误版本，同时在正确程序上保持通过。
