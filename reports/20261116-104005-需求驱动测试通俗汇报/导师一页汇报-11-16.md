# 测试演化与需求驱动测试研究进展

2026年11月17日更新

## 一、测试演化——软件更新后，自动更新旧测试

**研究动机。** 软件接口、依赖或功能发生变化后，原来的测试也需要更新。任务包括识别哪些测试需要修改，以及完成修改，使测试适应新版本并保留检查能力。

**数据集输入与输出。** PRBench、Updates4J提供代码的新旧版本、相关变更和旧测试，方法输出适用于新版本的测试代码。例如，测试原来通过`ReflectionUtility.getField(...)`读取对象状态，依赖更新后需要改用`Deencapsulation.getField(...)`。

**已完成工作。** 复现MuMuTestUp、TestUpdater、TestSyncer，统一使用GPT-6 Luna、medium，保留各方法自身流程。两个数据集共766条任务，得到2,298条生成记录。

**三种方法的主要思路。**

- **MuMuTestUp**：先收集相关代码上下文，再结合执行错误、覆盖率和变异测试反馈，多轮修改测试，提升可执行性和检错能力。
- **TestUpdater**：让模型提出更新测试所需的上下文，收集、筛选后生成新测试，再根据编译和运行错误修正。
- **TestSyncer**：分析代码变化类型、相关依赖定义和调用位置，将这些信息组织进提示词，引导模型更新旧测试。本次采用作者提示词构造流程进行单次生成。

|数据集|MuMuTestUp测试通过率|TestUpdater测试通过率|TestSyncer测试通过率|
|---|---:|---:|---:|
|PRBench，571条|87.7%|75.8%|37.0%|
|Updates4J，195条|91.3%|77.4%|65.1%|

测试通过率衡量更新后的测试能否在新版本正常执行，覆盖率和变异分数进一步衡量其检查能力。项目级任务还需要评价测试位置识别的准确率和召回率。

**后续发展。** 测试演化进一步发展到项目级的定位与更新。TEBench提供整个仓库和一次代码变更，要求Agent先找出哪些旧测试需要修改、哪些新行为需要补测试，再生成测试补丁，包含10个Java项目、314条任务。它同时考虑运行失败的旧测试、仍能通过但检查内容已经过时的旧测试，以及缺失的新测试。任务范围从“给定旧测试后更新”，扩展到“在整个项目中定位并完成更新”。

**为什么转向需求驱动测试。** 在本次两个数据集上，最强方法的测试通过率已达到87.7%和91.3%，继续提高通过率的空间相对有限。通过率仍需结合缺陷检出能力判断，项目级测试位置识别也仍有研究空间。但我们最初考虑的上下文收集、执行反馈等改进已被已有方法采用，目前尚未找到证据充分的独立切入点。因此，研究重点转向新功能开发中的需求验证，利用已有复现结果调查更具体的问题。

## 二、需求驱动测试——根据用户要求生成能发现错误的测试

**研究动机。** Coding Agent已经能够根据自然语言需求开发软件，但软件能运行、已有测试能通过，仍不能充分说明它满足了用户要求。因此，需要从用户需求出发生成测试，检查软件实际行为是否符合预期。

两个Benchmark分别把这件事落实到不同层面。**TestSuiteBench从完整软件规格生成整套测试**，例如根据目录管理工具的功能说明，检查添加、查询、删除和参数错误处理。**Req2Test-Bench从具体业务场景生成测试步骤**，例如根据“已有页眉的文档新增一节后应继承页眉”，准备文档、执行操作并检查结果。

两者共同关注的是，生成的测试能否发现违反需求的实现。我们的复现进一步发现，即使要求已经写清楚，测试仍可能没有准备必要状态，或没有检查指定结果。因此，希望研究**怎样把用户需求准确落实为有判别能力的测试，用来验收Coding Agent交付的软件是否符合预期。**

### 任务与复现结果

统一使用 **Codex CLI + GPT-6 Luna，medium**。

|Benchmark|输入的具体形式|生成的输出|本次结果|
|---|---|---|---|
|TestSuiteBench|一整个软件的英文功能说明书，写明命令、参数、结果和出错规则。例如zoxide说明目录如何添加、查询和删除|整套可执行测试及运行脚本。例如`test_cli.py`、`run.sh`|165条，Validity 74.67%，Mutation Score 16.11%|
|Req2Test-Bench|一个Given/When/Then场景，加上允许访问的项目接口与上下文。例如“已有页眉页脚的文档新增一节后，应继承前一节”|与场景配套的测试步骤代码。例如`features/steps/doc_add_section.py`|固定160条、计分159条，Pass@1 27.57%，KillComplete@1 12.53%|

Validity表示测试在正确软件上的通过比例，Mutation Score表示检出官方故意改错版本的比例。Pass@1表示任务执行通过率，KillComplete@1表示通过且检出全部计分变异的任务比例。Req2Test这两个百分比按官方项目等权计算，160条中共有44条通过、20条达到KillComplete。

### 问题一，功能级测试难以落实细粒度需求条件

Agent能围绕一个功能生成测试，却容易遗漏其中明确规定的异常条件、边界条件和组合限制。功能已有测试，仍可能有具体要求没有被检查。

**真实案例 · TestSuiteBench · zoxide目录管理工具**，任务`ajeetdsouza__zoxide.67ca1bc`。

**原始规格。** “Repeated scalar options such as `--score` and `--from` are usage errors.” 即同一次命令重复填写单值参数，应报参数错误。

```python
# 生成测试检查了分数不是数字
call("add", "--score", "x", "/tmp")
# 但没有构造重复参数输入，例如
# add --score 1 --score 2 /tmp
```

Agent轨迹显示已读取规格，并表示覆盖参数解析。最终套件检查了缺少参数、分数非法等情况，遗漏重复参数。官方变异在`src/cmd/cmd.rs`中设置`args_override_self = true`，允许后一个值覆盖前一个值，该变异存活。整个套件检出8/39个计分变异。

**拟研究的问题。** 如何识别一个功能中尚未落实到测试输入和检查的具体条件？用例名称和功能覆盖不能直接代表细粒度要求已覆盖。

### 问题二，测试步骤与真实业务行为脱节

测试写出了准备、操作和检查步骤，但这些步骤可能没有建立所需状态，或用测试自己构造的逻辑替代真实业务过程。

**真实案例 · Req2Test-Bench · python-docx文档处理**，任务`python-docx/features/doc-add-section.feature:16`。

```gherkin
Given a single-section Document object with headers and footers as document
When I execute section = document.add_section()
Then section.header.is_linked_to_previous is True
```

**需求含义。** 先准备真正带有页眉页脚的Word文档，新增一节后，检查它是否继承前一节。生成测试的关键代码为

```python
getattr(original_section, "header")  # 取得页眉代理对象
context.section = context.document.add_section()
assert context.section.header.is_linked_to_previous is True
```

Agent将读取六种页眉页脚属性用作准备步骤，但读取代理没有建立实际页眉页脚定义。也就是说，测试要检查“继承已有页眉”，起点却没有实际页眉。

官方变异`5d6e664690271921`删除新增节时清理页眉页脚引用的操作。参考测试检出，生成测试仍通过；该任务整体检出112/113个计分变异。

**拟研究的问题。** 如何确认准备和操作真正产生了需求规定的状态与行为，并从被测程序取得验证证据？后续分别检查状态理解错误和主动替代真实操作的情况。

### 问题三，需求约束在断言转换中被弱化

相关场景已经执行，但对象关系、检查范围或具体结果没有完整进入断言，违反需求的结果仍可能被接受。

**真实案例 · Req2Test-Bench · e-petitions请愿网站**，任务`e-petitions/features/charlie_creates_a_petition.feature:6`。

用户创建请愿前，网站列出相似请愿。原始需求要求标题和签名人数正确对应。

|标题原文|中文意思|签名人数|
|---|---|---:|
|Do not remove rioters benefits|不要取消暴乱者的福利|1,023|
|Rioters should loose benefits|应该取消暴乱者的福利|835|

生成测试执行了真实页面流程，但只在整个页面上分别查找标题和人数。

```ruby
table.raw.each do |action, signatures|
  expect(page).to have_content(action)
  expect(page).to have_content(signatures)
end
```

如果两条请愿的人数显示反了，标题和数字仍然都在页面上，这组断言依然满足。就像购物页面两件商品的价格标反了，检查商品名和价格都出现，仍发现不了对应错误。参考测试在同一条请愿区域内核对标题和人数。

该任务执行通过，检出172/183个变异。人数交换是根据代码推导的反例，尚未动态复现，也未将11个存活变异归因于这一缺口。

**拟研究的问题。** 如何保留需求明确规定的对应关系和结果限定，同时避免加入错误或无依据的期望？需要同时评价能否检出错误，以及是否误拒正确实现。

### 当前进展与下一步

三个候选问题分别关注条件覆盖、业务行为和结果判定。第一项已有TestSuiteBench证据，第二项主要由Req2Test仓库场景支持，第三项在两个Benchmark中均有案例。已有分析在Req2Test的44条通过任务中确认8条业务验证缺口，涉及7个项目，占18.18%；TestSuiteBench已定向分析6条，整体发生比例还需统计。

1. 对固定165条TestSuiteBench和160条Req2Test逐任务分类，分别统计执行失败、业务验证缺口与证据不足任务的数量、比例及项目分布，再结合轨迹核对原因。
2. 对照TELPA的对象准备与调用依赖分析，以及TOGLL、ChatAssert的断言生成研究，明确已有方法的适用范围。
3. 分别补充遗漏条件、修正真实状态或调用、调整断言约束，开展独立最小干预验证，检查是否提升检错能力并保持正确实现通过。
