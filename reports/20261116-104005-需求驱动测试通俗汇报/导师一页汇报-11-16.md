# 测试演化与需求驱动测试研究进展

2026年11月17日更新

## 一、测试演化——软件更新后，自动更新旧测试

**研究动机。** 软件接口、依赖或功能发生变化后，原来的测试也需要更新。任务包括识别哪些测试需要修改，以及完成修改，使测试适应新版本并保留检查能力。

**数据集输入与输出。** PRBench、Updates4J提供代码的新旧版本、相关变更和旧测试，方法输出适用于新版本的测试代码。例如，测试原来通过`ReflectionUtility.getField(...)`读取对象状态，依赖更新后需要改用`Deencapsulation.getField(...)`。

**已完成工作。** 复现MuMuTestUp、TestUpdater、TestSyncer，统一使用GPT-6 Luna、medium，保留各方法自身流程。两个数据集共766条任务，得到2,298条生成记录。

|数据集|MuMuTestUp测试通过率|TestUpdater测试通过率|TestSyncer测试通过率|
|---|---:|---:|---:|
|PRBench，571条|87.7%|75.8%|37.0%|
|Updates4J，195条|91.3%|77.4%|65.1%|

测试通过率衡量更新后的测试能否在新版本正常执行，覆盖率和变异分数进一步衡量其检查能力。项目级任务还需要评价测试位置识别的准确率和召回率。

**研究重点调整。** 给定旧测试后的更新已有较强基线，上下文收集和执行反馈等思路已有相关工作覆盖，目前尚未找到清楚的差异化切入点。后续重点转向需求驱动测试，研究AI开发新功能时，如何在缺少旧测试的情况下，根据用户需求发现实现错误。

## 二、需求驱动测试——根据用户要求生成能发现错误的测试

**研究动机。** 软件能够运行，业务结果仍可能出错。需求驱动测试要求AI把用户要求转成具体操作和断言，检查软件是否真正满足需求。

### 任务与复现结果

统一使用 **Codex CLI + GPT-6 Luna，medium**。

|Benchmark|输入的具体形式|生成的输出|本次结果|
|---|---|---|---|
|TestSuiteBench|一整个软件的英文功能说明书，写明命令、参数、结果和出错规则。例如zoxide说明目录如何添加、查询和删除|整套可执行测试及运行脚本。例如`test_cli.py`、`run.sh`|165条，Validity 74.67%，Mutation Score 16.11%|
|Req2Test-Bench|一个Given/When/Then场景，加上允许访问的项目接口与上下文。例如“已有页眉页脚的文档新增一节后，应继承前一节”|与场景配套的测试步骤代码。例如`features/steps/doc_add_section.py`|固定160条、计分159条，Pass@1 27.57%，KillComplete@1 12.53%|

Validity表示测试在正确软件上的通过比例，Mutation Score表示检出官方故意改错版本的比例。Pass@1表示任务执行通过率，KillComplete@1表示通过且检出全部计分变异的任务比例。Req2Test这两个百分比按官方项目等权计算，160条中共有44条通过、20条达到KillComplete。

### 初步问题一，需求写出了条件，测试却没有准备到位

**TestSuiteBench · zoxide**，任务`ajeetdsouza__zoxide.67ca1bc`。

原始规格为“Repeated scalar options such as `--score` and `--from` are usage errors.”，即同一次命令重复填写单值参数，应报参数错误。

```python
# 生成测试检查了分数不是数字
call("add", "--score", "x", "/tmp")
# 整个套件缺少重复参数输入，例如
# add --score 1 --score 2 /tmp
```

官方变异在`src/cmd/cmd.rs`中设置`args_override_self = true`，使重复参数被接受、后一个值覆盖前一个值。该变异存活，说明测试缺少触发这项错误的输入。

**Req2Test · python-docx**，任务`python-docx/features/doc-add-section.feature:16`。

```gherkin
Given a single-section Document object with headers and footers as document
When I execute section = document.add_section()
Then section.header.is_linked_to_previous is True
```

需求要求先有实际页眉页脚，再新增节、检查继承。生成测试的准备代码只读取属性。

```python
getattr(original_section, "header")  # 取得代理对象
context.section = context.document.add_section()
assert context.section.header.is_linked_to_previous is True
```

读取属性没有建立实际页眉定义。官方变异`5d6e664690271921`删除新增节时清理页眉页脚引用的操作，参考测试检出，生成测试仍通过。该任务检出112/113个变异，遗漏的这一项对应需求中未落实的准备状态。

**值得调查的问题。** 需求里的“已有某种状态”，怎样对应到仓库中真正建立该状态的操作？接口调用成功，仍可能没有满足测试的前提。

### 初步问题二，操作执行了，断言却只检查部分要求

**TestSuiteBench · rnr**，任务`ismaelgv__rnr.fc0733b`。

原始规格要求“Running with no command prints the complete main help to stderr and no stdout.”，即无参数启动应输出完整帮助。

```python
p = run([], work)
assert p.returncode == 2 and p.stdout == ''
assert p.stderr.startswith('RnR is a command-line tool')
```

测试只检查帮助文本的开头。官方`repo_1`变异删除帮助中的`to-ascii`命令说明后，这段测试仍通过。整个套件检出11/72个计分变异。

**Req2Test · Kapua**，任务`kapua/service/account/test/src/test/resources/features/AccountService.feature:120`。

```gherkin
Given I expect the exception "KapuaEntityNotFoundException" with the text "The entity of type account with id/name"
When I delete a random account
Then An exception was thrown
```

需求指定了异常类型和消息，生成测试却只记录“出现异常”。

```java
catch (KapuaException e) {
    stepData.put(EXCEPTION_CAUGHT, true);
    return;
}
```

官方变异`f9696266b289835c`把异常消息格式化函数的返回值改为`null`。参考测试检出，生成测试仍通过，该任务检出22/43个计分变异。

**值得调查的问题。** 怎样让需求中的具体结果、对象关系和异常限制完整进入断言？目前测试可能执行了正确操作，却接受了错误结果。

### 当前进展与下一步

两个Benchmark均已找到上述两类真实案例。已有分析在Req2Test的44条通过任务中确认8条业务验证缺口，涉及7个项目，占18.18%；TestSuiteBench已定向分析6条，整体发生比例还需统计。

1. 结合已有生成记录，继续核对条件准备和断言转换在哪一步出现遗漏，补充同类案例与成功对照。
2. 对照TELPA的对象准备与调用依赖分析，以及TOGLL、ChatAssert的断言生成研究，明确已有方法的适用范围。
3. 优先调查“需求明确写出的限制为什么没有进入断言”，形成可验证的研究问题，再确定后续方案。
