# PyTester、Sakura、IntentionTest 的研究问题

本次补充阅读三篇作者原文，核对动机、生成条件和评价证据。关于贡献之间关系的判断来自论文内容，评审录用原因未经核实。

| 论文 | 已有方法哪里不够 | 本文做法及证据 |
|---|---|---|
| PyTester（JSS 2025） | 开发者想在实现前写测试，依赖源码的生成器此时无法工作；不同输入可以同样有效，拟合唯一参考测试限制了训练目标 | 在 APPS 的题目描述上训练文本到 Python 测试生成模型，把语法、执行和覆盖反馈用于强化学习。生成时与训练时的权限不同。[作者论文](https://arxiv.org/abs/2401.07576) |
| Sakura（ISSTA 2026） | 真实开发者测试往往需要多个类、连续调用和一系列检查，文字描述没有写出每一步对应的具体 API | 拆解场景，用静态分析找类和方法，组合测试并根据执行反馈修正。证据包括编译率和与开发者测试的覆盖重合。20 个项目的 488 个参考测试各有三种反推描述。[作者论文](https://arxiv.org/html/2606.00530v3) |
| IntentionTest（ISSTA 2026） | 即使知道焦点方法，也有多种合法验证目的；覆盖相同代码可以验证不同的行为。项目特有的对象准备和验证也难重建 | 给定焦点源码与目标、前置、期望，检索同仓库可复用测试后按意图编辑。用通过率和与参考测试杀死的变异体集合重合等指标评估。Spark 创建服务器例中，方法无分支，开发者仍可能专门关心线程池选项。[作者论文](https://arxiv.org/html/2507.20619v4) |

前者回答实现前如何训练有效的生成器；后两者的核心差别在于如何把跨类场景定位、组装出来，以及如何在焦点已知时验证指定意图。两篇的手段和评价有重叠，单靠更换数据、模型或术语无法表明新增贡献。进一步选题需要证明现有强方法在什么具体现象上失败，有什么可独立验证的改进。
