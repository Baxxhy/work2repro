# 测试演化与需求驱动测试研究进展

2026年11月17日更新

## 一、测试演化

**研究任务。** 软件更新后，自动修改旧测试，使它适应新版本，并继续发现功能错误。

**已完成工作。** 复现三种方法，统一使用GPT-6 Luna、medium，在PRBench和Updates4J共766条任务上完成实验。

- **MuMuTestUp**结合执行错误、覆盖率和变异测试反馈，多轮更新测试。
- **TestUpdater**按需收集相关代码，再根据编译和运行错误修正测试。
- **TestSyncer**分析代码变化类型、依赖和调用位置，引导模型更新测试。

|数据集|MuMuTestUp通过率|TestUpdater通过率|TestSyncer通过率|
|---|---:|---:|---:|
|PRBench，571条|87.7%|75.8%|37.0%|
|Updates4J，195条|91.3%|77.4%|65.1%|

**方向调整。** 给定旧测试后的更新已有较高通过率，我们考虑的上下文补充、执行反馈等思路也已有工作采用，目前尚未找到明确切入点。该方向正在向项目级发展，例如TEBench要求从整个仓库中找到需要修改或新增的测试，再完成更新。我们将研究重点转向根据用户需求生成测试，验证新开发功能是否符合预期。

## 二、需求驱动测试

**研究动机。** Coding Agent已经能够根据自然语言需求开发软件，但程序能运行、测试能通过，仍可能没有满足用户要求。希望直接根据原始需求生成测试，用来验收Coding Agent交付的软件。

**两个Benchmark的数据特点。** 两者都根据英文自然语言生成测试，但任务粒度和可见信息不同。

|特点|TestSuiteBench|Req2Test-Bench|
|---|---|---|
|任务规模|165个命令行应用，全部复现|8个项目、eval共2,051条；本次汇报固定160条子集|
|输入形式|Markdown规格文件`spec.md`，按章节规定命令、参数、输出、异常和状态规则|Gherkin格式`.feature`文件，包含Feature、Background和目标Scenario，另提供接口声明及允许的仓库上下文|
|输入粒度|整个应用，规格中位数约5,635词、23节|一个具体场景；步骤明确，但对象初始化、共享状态和服务依赖仍需结合项目确定|
|项目语言|Rust、Go、C/C++|Java、PHP、Python、Ruby、Go|
|生成产物|整套黑盒测试；本次产物为Python/pytest测试和`run.sh`|项目原生测试步骤：Java/Cucumber、PHP/Behat、Python/behave、Ruby/Cucumber、Go/Godog|
|生成可见范围|默认仅规格，不提供生产源码或参考可执行程序|隐藏目标实现，保留接口声明及允许的项目上下文；参考测试不向Agent开放|

**输入实际形态。** TestSuiteBench的zoxide规格中有规则：`Repeated scalar options such as --score and --from are usage errors.`，即同一个分数或导入格式参数重复填写时必须报错。它是长规格中的一项规则，不是一道独立测试题。

Req2Test的CoreShop输入则是一个具体业务场景，例如以下原始步骤节选：

```gherkin
Scenario: Create a new order and add a product
  Given I add the product "T-Shirt" to my cart
  And I apply the voucher code "asdf" to my cart
  # 此处省略原始配送与账单地址步骤
  And I create an order from my cart
  Then there should be one product in my order
```

因此，“需求已经写清操作顺序”仍不等于“测试实现简单”：Agent还要把自然语言步骤接到项目中的真实对象、服务和检查入口。上述被测软件语言与测试代码语言并不总是相同，例如Rust程序可以用Python通过命令行测试。

**复现配置与结果。** 使用Codex CLI + GPT-6 Luna、medium。

|数据集|规模|主要指标|
|---|---|---|
|TestSuiteBench|165条|Validity 74.67%，Mutation Score 16.11%|
|Req2Test-Bench|固定160条，计分159条|Pass@1 27.57%，KillComplete@1 12.53%|

Validity和Pass@1反映测试在正确软件上能否通过；Mutation Score反映能检出多少故意引入的错误；KillComplete要求任务通过且检出全部计分变异。Req2Test指标按官方规则对项目等权平均。

### 初步发现的三个问题

**1. 细粒度需求条件覆盖不足。** 生成测试覆盖了主要功能，但遗漏需求明确规定的输入条件和异常规则。

**案例：TestSuiteBench / zoxide。** 原始规格以`spec.md`提供，规定重复输入同一分数参数必须报错。生成测试覆盖缺失参数、非法数值，却未覆盖重复参数。官方变异将其改为“接受重复参数并采用最后一个值”，生成测试未检出。

生成代码中的错误输入列表如下（仅调整排版，省略用例名称）：

```python
@pytest.mark.parametrize("args", [
    ("add",),
    ("init",),
    ("import",),
    ("add", "--score", "x", "/tmp"),
])
def test_usage_errors_are_status_two(ctx, args):
    *_, call = ctx
    r = call(*args)
    assert r.returncode == 2 and not r.stdout and r.stderr.startswith(b"error:")
```

列表中没有重复`--score`的输入，例如`add --score 1 --score 2 /tmp`。该命令是说明遗漏条件的示例，不属于原生成测试。

**2. 测试场景构造与真实业务执行脱节。** 测试通过简化对象或局部逻辑完成检查，未建立需求要求的业务状态或调用真实业务过程。

**案例：Req2Test-Bench / CoreShop。** 原始需求以`.feature`中的场景提供：购物车加入T恤、应用优惠券、填写地址并生成订单，最终订单包含一件商品。生成测试使用本地数组和匿名订单对象检查商品数量，没有调用购物车转订单服务。轨迹显示，Agent在集成困难后主动采用替代实现。该任务执行通过，但未检出200个计分变异；其中各变异的具体漏检原因尚未逐一确认。

生成代码的关键片段如下（省略注释和无关方法）：

```php
public function addProductToCart(string $product): void
{
    $this->items[] = $product;
}

public function createOrderFromCart(): void
{
    $this->order = new class($this->items) {
        public function __construct(private array $items) {}
        public function getItems(): ?array { return $this->items; }
    };
}

public function orderHasOneProduct(): void
{
    Assert::notNull($this->order, 'No order was created from the cart.');
    Assert::count($this->order->getItems(), 1);
}
```

商品进入测试自己的数组，再由匿名对象直接返回。整个检查没有经过真实订单服务。

**3. 需求关系约束向断言转换时丢失。** 测试执行了相关场景，但断言仅检查孤立属性，未验证需求规定的对象关系和结果限制。

**案例：Req2Test-Bench / e-petitions。** 原始`.feature`场景要求两项请愿分别显示对应标题及1,023、835个支持者。生成测试分别检查标题和人数是否出现在整个页面，未限定在同一请愿条目中。因此，交换两项人数仍满足这些断言。该缺口已由生成代码确认，尚未进行交换错误的动态验证。

生成代码中的对应检查：

```ruby
Then("I should see the following similar petitions:") do |table|
  table.raw.each do |action, signatures|
    expect(page).to have_content(action)
    expect(page).to have_content(signatures)
  end
end
```

两条断言的检查范围都是整个页面，没有要求标题与人数出现在同一条请愿记录中。

### 为什么出现这些问题：从轨迹进一步定位原因

|问题|代码与轨迹揭示的具体机制|当前判断|
|---|---|---|
|需求条件覆盖不足|zoxide轨迹执行过读取规格的命令，最终也声称覆盖参数解析，但生成列表没有重复参数输入。功能级完成判断没有落实到每项条件的用例核对|遗漏位于规格读取后的测试设计环节；尚不能断定是阅读遗漏、优先级选择还是预算影响|
|场景构造与业务脱节|CoreShop读取接口契约并查找上下文后，明确选择用本地数组记录购物车和订单，最终承认未调用生产订单服务|本例已确认：集成受阻后，以替代实现完成交付，验证范围随之偏离目标业务|
|关系约束在断言中丢失|e-petitions把表格中同一行的标题与人数拆成两次全页匹配；两次生成期执行又因缺少准备辅助方法中断，未获得完整场景反馈|已确认关系被拆散、观察范围过宽；执行反馈中断是伴随条件，尚未证明它导致了弱断言|

**更深一层的技术困难是：** 需求条款需要落实为可区分的测试输入，业务步骤需要落实为真实状态和调用，结果关系需要落实为正确范围内的断言。这三种对应关系不能通过“文件生成成功、语法正确、参考实现上通过”自动确认。它们是待研究的具体困难，不是三个已经证明的统一模型根因。

### 证据规模与后续工作

Req2Test的44条通过任务中，已确认场景与状态问题4条、业务约束判定问题5条，去重后为**8条（18.18%），涉及7个项目**。TestSuiteBench已确认条件遗漏2条、约束判定不足4条，去重5条，尚未完成165条任务的全量语义审核。

下一步利用已有产物，区分“必要信息未找到”“已找到但操作效果判断错误”“集成受阻后主动替代”“关系在断言中丢失”，逐任务记录比例，并选择同项目成功对照。结合TELPA的对象构造与依赖分析、TOGLL的测试预言机研究，判断哪些困难已有方法能够处理，哪些仍需要深入验证。本轮不新增模型生成或评测。
