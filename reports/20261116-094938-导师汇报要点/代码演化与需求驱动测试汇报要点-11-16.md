# 导师汇报要点

## 一、代码演化

- 动机。软件更新以后，接口、依赖或行为会发生变化，原有测试也需要同步修改。希望研究如何自动找到测试中需要一起修改的位置，减少人工维护，并保留有效检查。
- 数据集。PRBench本次571条Java任务，Updates4J本次195条Java任务。每条以代码前后版本、旧测试、被测代码及变更上下文作为更新材料，各方法按其流程选取上下文。输出是在新版本上运行的更新后测试。开发者更新后的测试用于参考分析。
- 配置。复现MuMuTestUp、TestUpdater、TestSyncer，统一使用GPT-6 Luna、medium，保留各方法自身流程和反馈轮次。两套数据共766条，三方法共2298条最终记录。

|数据集|MuMuTestUp测试通过率|TestUpdater测试通过率|TestSyncer测试通过率|
|---|---:|---:|---:|
|PRBench，571条|501/571，87.7%|433/571，75.8%|211/571，37.0%|
|Updates4J，195条|178/195，91.3%|151/195，77.4%|127/195，65.1%|

- 质量评测另检查覆盖率和变异检出。原1601条通过记录中1578条完成质量评测，23条仍有评测异常。
- 真实案例。PRBench的cucumber-reporting第47条，旧测试通过ReflectionUtility.getField(page, "context", VelocityContext.class)读取内部状态，开发者改为Deencapsulation.getField(page, "context")。三种方法在该任务均编译失败，TestSyncer记录明确指出ReflectionUtility无法解析。执行过程为生成更新测试、在新版本编译、旧辅助类无法解析、测试未能执行。该案例反映测试辅助依赖迁移被遗漏。
- 值得研究的原因。测试能否继续工作取决于被测方法及其辅助依赖。PRBench有326条任务的被测方法前后文本相同，这一组的通过率分别为86.5%、64.1%、11.0%。现象提示需要检查其他位置的变化如何影响测试。具体根因仍按案例核对。

历史复现依据 [三方法报告](https://github.com/Baxxhy/work2repro/blob/ab70364/reports/test-evolution-20261108/测试演化三方法复现与研究问题分析.md)。历史提交保留按用户要求暂时从main移除的三方法材料，本次只引用已有材料。

## 二、需求驱动测试

- 动机。开发者通过自然语言提出功能，AI可以生成实现。需要进一步生成测试，检查实现是否满足用户需求，尤其要发现能运行但业务行为错误的情况。
- TestSuiteBench。输入完整软件功能规格，输出可执行的应用级测试套件。本次全部165条。例如rnr规格规定命令错误时的退出码、诊断和帮助内容，生成测试调用程序、读取输出并进行断言。规格中还包括正常业务操作，应由套件共同验证。
- Req2Test-Bench。输入具体Gherkin需求场景及允许访问的仓库上下文，输出可执行步骤定义代码。本次固定8个项目，每项目20条，共160条，官方计分159条。例如给定商店和客户、完成下单、管理员应看到订单使用USD，模型需编写对应准备、下单和查询检查代码。
- 配置。Codex CLI 0.160.0、GPT-6 Luna、medium。TSB只做test_gen，生成超时6小时。Req2Test采用TH视图，生成超时1小时、最多200次模型调用。生成过程遵循允许视图，原评测按锁定官方入口执行。每条任务保留一个正式结果。

- 指标含义。Validity衡量正确实现上测试用例通过情况，Mutation Score衡量人为修改后的错误版本被测试识别的情况。Req2Test的Pass@1检查生成结果能否通过；KillComplete要求检出该任务全部官方计分变异；API F1、Coverage J、Mutation R分别比较与参考测试的API使用、代码覆盖和变异检出。Req2Test表中为官方按项目等权聚合，不能用总通过条数相除代替。
- 真实代码案例。Sylius的placing_an_order_on_a_single_channel_store.feature:20要求管理员看到订单币种。生成代码实际执行commandBus.dispatch(new CompleteOrder(...))，保存placed_order，随后从sharedStorage取回该对象，检查getCurrencyCode()。它没有通过管理员接口重新查询。
- 实际执行记录。正确实现上测试通过；候选与参考记录都执行了CompleteOrderHandler；候选最后读取原对象；参考最后通过管理员API查询并检查currencyCode。候选杀死260/402个计分变异，142个存活。142个修改位置中119个在候选基线中未被执行到，23个执行到但变异仍通过。这些数量对应已有记录，不把它们全部归为管理员路径遗漏。
- 人话解释。订单对象写着USD，管理员查询仍可能返回错误数据。测试只查原对象，会漏掉管理员实际看到的结果。这是值得处理的业务风险。
- 当前发现。固定子集44条通过任务已完成静态需求对照，8条存在业务检查缺口，占18.18%，涉及7个项目。TSB已详细检查6条，其中4条支持局部需求遗漏或检查不足，165条总体语义比例仍待补齐。
- 当前研究问题。第一，需求中的业务状态如何对应到仓库里的正确准备、操作和读取路径。第二，需求中的对象关系和限定条件如何完整表达成断言。继续结合已有生成轨迹定位原因，并检查成功指标是否能反映需求验证质量。

### 代码演化的定位

当前关注项目级变更影响下的测试演化，可以理解为项目某处改动后，哪些测试需要跟着改，以及怎么改。识别受影响位置是其中一个环节。当前复现任务主要给定待更新旧测试，尚未完成从整个仓库自动找全受影响测试的实验。已有方法也使用项目上下文，后续需要分析其仍遗漏的关联变化。

PRBench真实记录`prbench:damianszczepanik/cucumber-reporting:47`包含旧提交281d313、新提交daf1dad、旧测试和相关生产代码变化。被测函数buildGeneralParameters的局部变化为LOG.error变成LOG.warn。旧测试仍通过ReflectionUtility.getField读取context，检查context有6个字段且build_time非空。开发者参考测试改成Deencapsulation.getField(page, "context")，保留这两个断言。三方法本次均编译失败，TestSyncer明确报旧辅助类无法解析。因此，给定方法内部的局部改动不足以说明测试需要完成的辅助依赖修改。

### TestSuiteBench的一条输入与实际生成输出

真实任务`ismaelgv__rnr.fc0733b`的spec.md说明这是批量重命名工具。Spec 5明确规定默认是预览模式，打印计划但不执行重命名。其他规格还规定替换、备份、递归、撤销和错误输出。

实际生成的test_default_preview_and_no_match包含以下片段。

```python
(work / 'test-aaa-bbb.txt').write_text('payload')
p = run(['regex', '-', '_', 'test-aaa-bbb.txt'], work)
assert p.returncode == 0 and p.stderr == ''
assert p.stdout == 'This is a DRY-RUN\ntest-aaa-bbb.txt -> test_aaa-bbb.txt\n'
assert (work / 'test-aaa-bbb.txt').exists() and not (work / 'test_aaa-bbb.txt').exists()
```

这段代码准备一个文件，调用工具，检查预览文字，再确认旧文件仍在、新文件未产生。若某个错误实现预览时真的改了文件名，这些文件存在性断言可以发现问题。这是用于解释检查能力的条件推演，本轮没有注入该错误重新运行。

## 输入输出口径澄清

本轮核对原始生成提示及Req2Test任务JSON，以下区分用于汇报。

|项目|TestSuiteBench本次test_gen|Req2Test-Bench本次TH视图|
|---|---|---|
|提供给生成Agent的核心材料|完整程序spec.md与测试运行约定|固定Gherkin场景、背景条件、允许访问的项目上下文、目标接口和测试框架约定|
|接触被测软件的方式|围绕命令行程序的外部行为编写测试；评测时在新工作区提供/workspace/executable|在项目测试框架中实现步骤，可使用允许的接口及上下文；目标实现和指定辅助实现被隐藏|
|交付文件|/workspace/eval中的测试套件、辅助文件、可执行run.sh；运行后写results.xml|指定可接受目录中的步骤定义代码及允许的支持文件，由官方框架运行固定场景|
|检查范围|完整软件规格中的多个功能|指定场景及其背景条件|

因此，TSB是一份完整程序说明到外部可运行测试套件；Req2Test是已给定业务步骤到项目内部可执行步骤代码。两者都用于检查实现是否违反需求，生成材料和测试形式各有明确约束。

PRBench与Updates4J的共同任务是更新给定旧测试。本仓库导出的JSON采用统一适配字段，因此字段相同不能证明原始数据组织或各方法提示相同。本次核对到Updates4J的klaw第0条具体涉及showActivityLog新增ordering参数，旧测试的三参数Mock需改为四参数；PRBench的cucumber-reporting第47条具体涉及测试辅助工具替换。不能将两者凭名称划成全仓定位任务与方法更新任务。
